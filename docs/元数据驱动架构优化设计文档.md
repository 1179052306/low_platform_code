# 元数据驱动架构优化设计文档

> 版本：v1.0
> 日期：2026-09-24
> 目标：在金蝶苍穹元数据驱动架构基础上进行**优化**，规划四个方向的改造方案
> 关联文档：低代码通用后台与插件架构设计文档（第 17 章）
> 状态：**方案设计阶段（未动代码）**

---

## 0. 文档目的

用户认可金蝶苍穹"元数据驱动"方向，尤其"一切皆元数据统一驱动"。本文档规划四个方向如何改造达到苍穹效果，并**在苍穹架构上做更好的优化**（指出苍穹不足 + 我们的改进），输出可落地的设计。

### 四个方向

| 方向 | 苍穹核心 | 本文档优化重点 |
|------|---------|---------------|
| 1. 元数据分层继承 | 产品/行业/客户三层合并 | 属性级覆盖、合并缓存、合并溯源、显式删除、冲突检测 |
| 2. 一切皆元数据统一驱动 | 一切皆元数据 | 分域子引擎、元数据依赖图、生命周期治理、命名空间 |
| 3. 元数据版本化 | 有版本可回滚 | 细粒度版本、兼容性自动检测、回滚安全检查 |
| 4. 应用包 | 整体打包部署 | 依赖声明解析、包组合冲突解决、增量包、兼容矩阵 |

### 设计原则

1. **优化而非照搬**：每个方向先分析苍穹不足，再给改进点
2. **可落地**：给数据模型、运行时机制、落地步骤
3. **四方向协同**：分层 + 统一 + 版本 + 包 互相支撑，不是孤立的
4. **渐进式**：可分阶段落地，不必一步到位

## 1. 方向一：元数据分层继承

### 1.1 苍穹做法

产品层（金蝶标准产品出厂）→ 行业层 → 客户层，运行时从下到上合并：上层继承下层所有字段/操作/布局，可新增（加字段）、可覆盖（改字段属性）。客户层只记录增量，不碰产品层。产品升级时客户层自动兼容。

### 1.2 苍穹不足（可优化点）

| 不足 | 问题 |
|------|------|
| **覆盖粒度粗** | 覆盖是整字段级，只想改字段一个属性（如只改 label 不改 type）也要整字段覆盖，容易把其他属性意外回退到下层值 |
| **合并性能** | 每次运行时合并三层，层数多/元数据大时有开销 |
| **合并黑盒** | 合并后看不出"这个字段哪层加的、哪个属性哪层改的"，调试难 |
| **删除语义模糊** | 上层想"删除"下层字段（而非覆盖），语义不清 |
| **冲突靠人工** | 字段重命名/类型变更等冲突靠升级工具人工处理，易错 |

### 1.3 我们的优化

#### 优化1：属性级覆盖（而非字段级）

覆盖记录到**属性粒度**——只记录本层改了哪个属性，不整字段覆盖。

```
产品层字段 amount: { type:decimal, label:"金额", required:true, scale:2 }
客户层只改 label → overrideProps: { label:"采购金额" }
合并结果: { type:decimal, label:"采购金额", required:true, scale:2 }
                                          ↑ 保留产品层，不意外回退
```

#### 优化2：声明式合并策略

每个属性声明合并策略，而非硬编码合并逻辑：

| 策略 | 含义 | 适用 |
|------|------|------|
| OVERRIDE | 上层值覆盖下层 | 字段属性（label/type/required） |
| MERGE | 上下层合并（去重） | 校验规则、事件订阅 |
| APPEND | 上层追加到下层列表 | 列表字段、操作按钮 |
| REJECT | 上层不允许改该属性 | 主键、字段名（防破坏） |

#### 优化3：合并结果缓存

合并后的元数据缓存（key = bizCode + 各层 version），不每次重新合并。任一层版本变更 → 失效重算。

#### 优化4：合并溯源

合并结果记录每个字段/属性来自哪一层（`sourceLayer`），支持可视化 diff："这个 label 是客户层改的，type 是产品层定义的"。便于调试和审计。

#### 优化5：显式删除

上层"删除"下层字段用显式 `removedFields` 声明，语义清晰，区别于"覆盖成空"。删除时校验：是否有业务数据/流程/权限依赖该字段，有则警告。

#### 优化6：冲突检测

保存时检测破坏性变更（改字段 type、缩 length、删字段），标记 `BREAKING`，要求显式迁移脚本（对接方向3），不静默通过。

### 1.4 数据模型

```sql
-- 元数据层定义
lc_meta_layer (
  id, layerType,          -- PLATFORM / INDUSTRY / CUSTOMER
  layerCode, layerName, parentLayer, priority   -- priority 决定合并顺序
)

-- 业务元数据增加分层字段
lc_biz_meta 增加:
  layerType, parentBizCode, baseVersion   -- baseVersion: 继承的父层版本

-- 字段元数据改为增量记录
lc_field_meta 增加:
  layerType, bizCode, fieldName,
  isNew,                  -- 本层新增的字段
  overrideProps,          -- 本层覆盖的属性（JSON，属性级，只记录改的）
  isRemoved,              -- 本层显式删除下层字段
  sourceLayer             -- 溯源：该字段最终来自哪层（合并后填）

-- 属性合并策略
lc_merge_rule (
  metaType, propName, strategy   -- OVERRIDE/MERGE/APPEND/REJECT
)
```

### 1.5 运行时合并机制

```
MetaRegistry.getMerged(bizCode):
  1. 取各层元数据（按 priority: PLATFORM → INDUSTRY → CUSTOMER）
  2. 检查缓存（key = bizCode + 各层 version），命中则返回
  3. 从 PLATFORM 开始逐层合并：
     for each layer in priority order:
       for each field in layer.fields:
         if field.isNew:        加入结果
         if field.isRemoved:    从结果移除（先校验依赖）
         if field.overrideProps: 按 lc_merge_rule 逐属性合并
           OVERRIDE: 结果[prop] = layer[prop]
           MERGE:     结果[prop] = merge(结果[prop], layer[prop])
           APPEND:    结果[prop] = 结果[prop] + layer[prop]
           REJECT:    忽略（不允许改）
         记录 sourceLayer（溯源）
  4. 缓存合并结果
  5. 返回合并元数据 + 溯源信息
```

### 1.6 落地步骤

1. `lc_biz_meta`/`lc_field_meta` 加 `layerType`/`parentBizCode`/`overrideProps` 等字段
2. 实现 `MetaMerger`（按 `lc_merge_rule` 合并）+ 缓存 + 溯源
3. 现有单层元数据迁移为 PLATFORM 层
4. 元数据配置页面支持选层编辑（客户层只显示增量编辑）
5. 合并 diff 可视化（哪个属性哪层改的）
6. 冲突检测 + BREAKING 标记

## 2. 方向二：一切皆元数据统一驱动

### 2.1 苍穹做法

一切皆元数据（业务对象/字段/操作/表单/列表/报表/流程/权限/校验/编号），统一存元数据库，运行时统一由元数据引擎驱动。

### 2.2 苍穹不足

| 不足 | 问题 |
|------|------|
| **引擎臃肿** | 一个引擎驱动所有元数据类型，越来越重，难维护 |
| **元数据耦合** | 类型间依赖复杂（流程引用字段、权限引用字段），变更影响难追踪 |
| **缺乏治理** | 元数据多了之后谁定义的、给谁用、是否冗余，无治理 |
| **类型膨胀** | 所有配置都是元数据，类型越来越多 |

### 2.3 我们的优化

#### 优化1：分域分类 + 独立子引擎（避免臃肿）

元数据按**域**分类，每域有独立子引擎，统一注册但独立驱动。避免苍穹一个臃肿引擎。

| 域 | 包含元数据 | 子引擎 |
|----|-----------|--------|
| **结构域** STRUCTURE | 业务对象/字段/关系 | CrudExecutor |
| **行为域** BEHAVIOR | 操作/状态机/事件/校验/编号 | ActionExecutor / StateMachine / EventBus / Validator |
| **展现域** PRESENTATION | 表单布局/列表布局/报表/打印 | RenderEngine |
| **控制域** CONTROL | 权限/流程/数据规则 | AuthEngine / WorkflowEngine |

统一 `MetaRegistry` 按 `metaType` 路由到对应子引擎，各子引擎独立演进。

#### 优化2：元数据依赖图（变更影响分析）

维护元数据间依赖关系，变更时做影响分析（第 14 章 F4）：

```
改字段 amount → 影响分析：
  - 表单布局 formA 引用了 amount → 提示
  - 校验规则 ruleB 依赖 amount → 提示
  - 流程节点 conditionExpr 引用 amount → 提示
  - 权限 dataScope 引用 amount → 提示
```

依赖图存 `lc_meta_dependency`，变更前查询受影响元数据，警告或阻止。

#### 优化3：元数据生命周期治理

元数据有状态：`DRAFT → PUBLISHED → DEPRECATED → ARCHIVED`。
- 废弃的元数据不再加载，但保留可查
- 定期归档清理冗余/无引用的元数据
- 每条元数据记录 `owner`（谁定义的）、`usageCount`（被引用次数），治理可见

#### 优化4：元数据命名空间

按业务域/模块分命名空间（如 `purchase`/`stock`/`finance`），避免全局 metaCode 冲突，支持按命名空间加载/导出（对接应用包）。

#### 优化5：统一元数据 API + 类型 Schema 校验

所有元数据走统一 API（`/api/lowcode/meta/{metaType}` CRUD），但每种 `metaType` 有自己的 JSON Schema 校验（保存前校验合法性，对应"建表校验前置"）。

### 2.4 数据模型

```sql
-- 统一元数据注册表
lc_meta_registry (
  id, metaType,           -- BIZ/FIELD/ACTION/FORM/LIST/REPORT/PERM/WORKFLOW/VALIDATION/NUMBER...
  metaCode, metaName,
  domain,                 -- STRUCTURE/BEHAVIOR/PRESENTATION/CONTROL
  namespace,              -- 业务域命名空间
  layerType, version, status,   -- status: DRAFT/PUBLISHED/DEPRECATED/ARCHIVED
  content,                -- 元数据内容（JSON，按 metaType 有不同 schema）
  owner, usageCount,
  createTime, updateTime
)

-- 元数据依赖图
lc_meta_dependency (
  id, fromMetaId, toMetaId, depType   -- depType: REFERENCE/EXTEND/CONDITION
)

-- 元数据类型 schema（校验用）
lc_meta_type_schema (
  metaType, jsonSchema    -- 每种元数据类型的 JSON Schema
)
```

### 2.5 运行时机制

```
MetaRegistry.load(metaType, metaCode):
  1. 查 lc_meta_registry（按 layerType 合并，见方向1）
  2. 按 domain 路由到子引擎
  3. 子引擎按 content 驱动执行

MetaRegistry.changeImpact(metaId):
  1. 查 lc_meta_dependency 反向依赖
  2. 返回受影响的元数据列表
  3. 标记 BREAKING 的阻止变更，否则警告
```

### 2.6 落地步骤

1. 建 `lc_meta_registry` 统一注册表，把现有 `lc_biz_meta`/`lc_field_meta` 等迁入（metaType=BIZ/FIELD）
2. 按域拆子引擎（现有 CrudExecutor/StateMachine 等已是子引擎，归域即可）
3. 建依赖图，实现变更影响分析
4. 元数据状态机（草稿/发布/废弃）
5. 命名空间划分
6. 统一元数据 API + 各类型 JSON Schema 校验

## 3. 方向三：元数据版本化

### 3.1 苍穹做法

元数据带版本号，变更存历史可回滚，产品升级时客户层自动兼容，有升级工具处理兼容性。

### 3.2 苍穹不足

| 不足 | 问题 |
|------|------|
| **版本粒度粗** | 整业务对象版本，单字段变更也整体新版本，版本爆炸 |
| **兼容靠人工工具** | 字段重命名/类型变更兼容靠升级工具人工处理，易错 |
| **回滚风险** | 回滚元数据可能影响已产生业务数据（字段已存数据，回滚删字段），处理不完善 |
| **多环境同步难** | 开发/测试/生产元数据版本同步靠人工 |

### 3.3 我们的优化

#### 优化1：细粒度版本

版本到**字段/属性粒度**：单字段变更只记该字段的版本变更，不整体新版本。减少版本爆炸，diff 精确。

```
v1.0: 业务对象 purchaseOrder 建立
v1.1: 字段 amount 的 scale 从 2 改到 4   ← 只记这一个属性变更
v1.2: 新增字段 projectCode              ← 只记新增
```

#### 优化2：兼容性自动检测

变更时自动判断破坏性：

| 变更 | 兼容性 | 处理 |
|------|--------|------|
| 新增字段 | COMPATIBLE | 直接通过 |
| 改 label/提示 | COMPATIBLE | 直接通过 |
| 改 type（如 decimal→string） | BREAKING | 要求迁移脚本 |
| 缩 length | BREAKING | 要求迁移脚本 |
| 删字段 | BREAKING | 检查是否有数据，有则要求归档脚本 |

BREAKING 变更必须附迁移脚本，走审批，不静默通过。

#### 优化3：回滚安全检查

回滚前检查业务数据依赖：
- 删字段回滚：该字段已有数据？有则提示"字段有数据，回滚将丢失，需先归档"
- 改 type 回滚：现有数据能否转换？不能则阻止
- 给出回滚影响清单，确认后才执行

#### 优化4：版本 diff 可视化 + 多环境同步走应用包

版本间 diff 可视化（哪个字段哪个属性变了）。多环境同步走应用包（方向4），不人工同步。

#### 优化5：向前兼容声明

每个版本变更声明 `compatibility`（COMPATIBLE/BREAKING），BREAKING 走审批 + 迁移脚本，COMPATIBLE 自动生效。

### 3.4 数据模型

```sql
-- 元数据版本历史（细粒度）
lc_meta_version (
  id, metaType, metaCode, version,
  changeType,            -- ADD_FIELD/MODIFY_PROP/REMOVE_FIELD/ADD_ACTION...
  changedField,          -- 变更的字段/属性（细粒度）
  oldValue, newValue,    -- 变更前后值
  compatibility,         -- COMPATIBLE / BREAKING
  migrationScript,       -- BREAKING 变更的迁移脚本
  content,               -- 该版本完整内容快照
  createTime, creator, approvedBy
)

-- 回滚安全检查
lc_meta_rollback_check (
  versionId, affectedDataCount, impactSummary, safe
)
```

### 3.5 运行时机制

```
MetaRegistry.change(metaId, change):
  1. 检测兼容性（自动判断 COMPATIBLE/BREAKING）
  2. if BREAKING: 要求 migrationScript + 审批
  3. 变更影响分析（方向2 依赖图）
  4. 写 lc_meta_version（细粒度记录）
  5. 更新 lc_meta_registry.content
  6. 失效合并缓存（方向1）

MetaRegistry.rollback(versionId):
  1. 回滚安全检查（数据依赖）
  2. 不安全则提示影响，确认后执行
  3. 恢复到该版本内容
```

### 3.6 落地步骤

1. `lc_meta_version` 表 + 变更历史记录
2. 兼容性自动检测器
3. BREAKING 变更审批流 + 迁移脚本执行
4. 回滚安全检查
5. 版本 diff 可视化
6. 与方向1（分层）协同：PLATFORM 层版本升级，CUSTOMER 自动兼容

## 4. 方向四：应用包

### 4.1 苍穹做法

应用包/开发方案：把一个业务领域的所有产物打包（元数据+插件+页面+权限+流程+配置），整体部署/迁移/升级，有版本。

### 4.2 苍穹不足

| 不足 | 问题 |
|------|------|
| **包内依赖黑盒** | 包引用外部（如标准产品字段），部署时依赖检查不充分 |
| **包升级冲突** | 新版包与已有数据/自定义冲突处理粗 |
| **包不可组合** | 组合多包（采购包+库存包）的依赖处理弱 |
| **缺兼容矩阵** | 包间兼容性不清晰 |

### 4.3 我们的优化

#### 优化1：包依赖声明 + 解析

包显式声明依赖（依赖哪些其他包、标准产品版本），部署时解析依赖树，缺失则报错，版本不匹配则警告。

```json
// manifest.json
{
  "packageCode": "purchase-management",
  "version": "1.2.0",
  "dependencies": [
    { "package": "base-data", "versionRange": ">=1.0.0" },
    { "package": "@platform/standard", "versionRange": ">=2.0.0" }
  ]
}
```

#### 优化2：包组合 + 冲突走分层继承

多包组合时，冲突（都改了同一字段）走**方向1 分层继承**解决，而非简单覆盖。每个包声明自己的 layerType，按层合并。

#### 优化3：增量包

支持增量包：只含相对基线版本的变更，减小体积。部署 = 基线包 + 增量包。

#### 优化4：包版本兼容矩阵

维护包间兼容性矩阵，部署前校验：purchase-management 1.2.0 是否兼容 base-data 1.1.0？不兼容则阻止。

#### 优化5：包与数据分离

包只含结构/配置，**不含业务数据**。数据迁移走单独脚本（方向3 的 migrationScript），避免包携带数据导致的环境数据污染。

#### 优化6：包市场（远期）

业务模板包市场，可发布/引用/安装标准业务包。

### 4.4 数据模型

```sql
-- 应用包
lc_app_package (
  id, packageCode, packageName, version,
  baselineVersion,        -- 基线版本（增量包用）
  layerType,              -- 包对应的层（组合冲突用）
  dependencies,           -- 依赖的其他包（JSON）
  contentUrl,             -- 包文件存储地址
  checksum, status,       -- DRAFT/PUBLISHED/INSTALLED
  createTime, creator
)

-- 包兼容矩阵
lc_app_package_compat (
  packageCode, version, dependsPackageCode, dependsVersionRange, compatible
)

-- 包安装记录
lc_app_package_install (
  id, packageCode, version, env,    -- env: DEV/TEST/PROD
  installTime, status, errorMsg
)
```

### 4.5 包结构

```
purchase-management-v1.2.0.zip
  ├── manifest.json          # 包清单：版本/依赖/兼容性/layerType
  ├── metadata/              # 元数据（按域分类，对接方向2）
  │   ├── structure/         # 业务对象/字段
  │   ├── behavior/          # 操作/状态机/事件/校验
  │   ├── presentation/      # 表单/列表/报表
  │   └── control/           # 权限/流程
  ├── plugins/*.jar          # 插件
  └── migrations/            # BREAKING 变更的迁移脚本（对接方向3）
```

### 4.6 部署流程

```
上传包 → 校验签名 + manifest
  → 解析依赖树（缺依赖则报错）
  → 兼容矩阵校验（不兼容则阻止）
  → 解包：元数据 → lc_meta_registry（按 layerType 入层）
           插件 → PluginContainer 加载
           迁移脚本 → 执行
  → 元数据合并缓存失效
  → 发布完成
```

### 4.7 落地步骤

1. 定义包结构 + manifest 规范
2. `lc_app_package` 表 + 依赖解析 + 兼容校验
3. 打包工具（把一个业务的元数据+插件打成 zip）
4. 部署引擎（解包 + 依赖校验 + 入库 + 插件加载）
5. 增量包支持
6. 包市场（远期）

## 5. 四方向协同关系

四个方向不是孤立的，互相支撑：

```
方向2（统一元数据）是基础
  ├── 方向1（分层继承）在统一元数据上加 layer 维度
  ├── 方向3（版本化）给统一元数据加版本历史
  └── 方向4（应用包）把统一元数据打包，包内元数据带层+版本

协同场景：
  - 平台发布标准产品 = 应用包（方向4）含 PLATFORM 层（方向1）元数据 + 版本（方向3）
  - 客户定制 = CUSTOMER 层增量元数据 + 插件，打成客户包
  - 运行时 = 统一引擎（方向2）加载各层元数据，按层合并（方向1），按版本（方向3）兼容
  - 升级 = 新版平台包部署，CUSTOMER 层通过继承自动兼容，BREAKING 变更走迁移脚本
```

| 协同点 | 方向 | 说明 |
|--------|------|------|
| 包内元数据带层+版本 | 1+3+4 | 应用包的元数据声明 layerType 和 version |
| 分层合并用统一引擎 | 1+2 | MetaRegistry 统一加载，按层合并 |
| 版本化基于统一元数据 | 2+3 | lc_meta_version 关联 lc_meta_registry |
| 变更影响分析跨域 | 2 | 依赖图跨结构/行为/展现/控制域 |
| BREAKING 变更走包迁移 | 3+4 | 包内 migrations 对接版本化迁移脚本 |

## 6. 落地路线图

### 6.1 阶段划分

| 阶段 | 内容 | 依赖 | 里程碑 |
|------|------|------|--------|
| **S1 元数据统一** | 方向2：统一注册表 + 分域子引擎 + 依赖图 | 无 | M1：现有元数据迁入统一注册表，统一 API |
| **S2 分层继承** | 方向1：layer + 属性级覆盖 + 合并 + 缓存 + 溯源 | S1 | M2：客户层加字段不改平台层，合并生效 |
| **S3 版本化** | 方向3：细粒度版本 + 兼容检测 + 回滚安全 | S1 | M3：元数据变更可追溯可回滚，BREAKING 拦截 |
| **S4 应用包** | 方向4：包结构 + 依赖解析 + 部署引擎 | S1+S2+S3 | M4：业务打包部署迁移 |
| **S5 治理增强** | 命名空间 + 生命周期 + 包市场 + diff 可视化 | S1~S4 | M5：元数据治理完整 |

### 6.2 优先级建议

```
S1（统一元数据）是地基，先做
  → S2（分层继承）价值最高，紧接做
  → S3（版本化）配合 S2，可并行
  → S4（应用包）等元数据稳定后做
  → S5（治理）渐进增强
```

**最优先**：S1 + S2。因为"一切皆元数据统一驱动"是地基，"分层继承"是最高价值（解决结构层扩展不改平台）。这两个做完，核心能力就具备了。

### 6.3 与现有方案的整合

| 现有 | 整合到 |
|------|--------|
| `lc_biz_meta`/`lc_field_meta` 等 | 迁入 `lc_meta_registry`（metaType=BIZ/FIELD），加 layerType |
| CrudExecutor/StateMachine/EventBus | 归为结构域/行为域子引擎 |
| 插件机制（第3章） | 保留，插件改行为；分层改结构，互补 |
| 字段变更事件（第13章） | 归行为域元数据，纳入统一管理 |
| 审批流（第16章） | 归控制域元数据 |
| 对外API映射（第15章） | 归行为域元数据 |
| 元数据缓存 | 复用现有基础数据缓存，合并结果缓存其上 |

## 7. 苍穹 vs 本方案优化对照

| 方向 | 苍穹 | 本方案优化点 |
|------|------|-------------|
| 分层继承 | 字段级覆盖、合并黑盒、删除模糊 | **属性级覆盖、声明式合并策略、合并缓存、溯源、显式删除、冲突检测** |
| 统一驱动 | 一个臃肿引擎、耦合难追踪 | **分域子引擎、依赖图影响分析、生命周期治理、命名空间** |
| 版本化 | 粗粒度、兼容靠人工、回滚风险 | **细粒度版本、兼容自动检测、回滚安全检查、向前兼容声明** |
| 应用包 | 依赖黑盒、组合弱 | **依赖声明解析、组合走分层、增量包、兼容矩阵、包数据分离** |

**核心优化理念**：苍穹是"大而全的统一引擎"，本方案是"**分域自治 + 统一注册 + 分层合并 + 版本安全 + 包化部署**"——统一但不臃肿，分层且可溯源，版本化且安全，包化且可组合。

## 8. 风险与应对

| 风险 | 等级 | 应对 |
|------|------|------|
| 现有元数据迁移到统一注册表工作量大 | 高 | 分批迁移，先迁核心（BIZ/FIELD），其余渐进 |
| 分层合并规则复杂，调试难 | 中 | 溯源 + diff 可视化 + 合并结果缓存可查 |
| 属性级覆盖实现复杂 | 中 | 先字段级覆盖落地，再升级属性级 |
| 依赖图维护成本 | 中 | 变更时自动更新依赖，定期校验 |
| BREAKING 变更迁移脚本编写负担 | 中 | 提供常见变更的自动迁移（如加字段自动 alter table） |
| 应用包依赖解析复杂 | 中 | 先支持单包部署，再支持多包组合 |
| 回滚影响业务数据 | 高 | 回滚安全检查强制，不安全阻止 |
