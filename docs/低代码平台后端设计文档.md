## 0. 文档目的

本文档针对用户提出的 6 项核心需求，给出低代码平台**通用后台引擎 + 插件扩展机制 + 事件驱动 + 事务一致性 + 本地调试**的整体架构方案，并由多个角色进行可行性评估，最终输出详细开发计划。本文档**不包含业务代码实现**，仅作为设计与评审基线。

### 0.1 需求原文归纳

| 编号 | 需求 | 关键约束 |
|------|------|----------|
| R1 | 前端是低代码平台（前提） | 后台必须与低代码前端契约契合 |
| R2 | 新增/修改/删除/下达/撤销等通过配置完成 | 通用后台，配置驱动，非硬编码 |
| R3 | 以插件方式完善定制化功能，本地开发上传，不修改原平台 | 插件隔离、热加载、不侵入平台 |
| R4 | 数据状态变化时可捕捉，自定义配置或开发业务代码 | 事件驱动，状态机可观测 |
| R5 | R3、R4 必须在同一事务中保持一致性 | 编程式事务，非方法间调用拼装 |
| R6 | 本地开发插件如何调试 | 本地 SDK + 远程热部署 + 断点调试 |

## 1. 总体架构设计

### 1.1 设计原则

1. **配置优先（Config-Driven）**：CRUD/下达/撤销等通用能力由元数据配置驱动，零代码即可上线一个业务单据。
2. **扩展开放（Open-Closed）**：平台对修改关闭、对扩展开放。定制化逻辑一律走插件，平台核心二进制不被改动。
3. **事务一体（Transactional Integrity）**：通用引擎执行、插件扩展、事件回调在同一物理事务内完成，失败整体回滚。
4. **可观测（Observable）**：状态变化即事件，事件可被配置订阅，也可被自定义代码订阅。
5. **可调试（Debuggable）**：插件可在本地 IDE 断点调试，并提供"本地代理 → 远程平台"的联调通道。

### 1.2 分层架构

### 1.3 核心模块职责

| 模块 | 包路径 | 职责 |
|------|--------|------|
| GenericGatewayController | `com.api.lowcode.gateway` | 统一 HTTP 入口，解析 `bizCode + action + payload`，分发到引擎 |
| MetaRegistry | `com.api.lowcode.meta` | 加载/缓存元数据配置（表、字段、状态机、动作绑定） |
| CrudExecutor | `com.api.lowcode.engine.crud` | 按 Meta 执行 insert/update/delete/query，含字段权限、数据规则 |
| StateMachine | `com.api.lowcode.engine.statemachine` | 下达/撤销等状态流转，校验迁移合法性，产出状态事件 |
| EventBus | `com.api.lowcode.engine.event` | 同步事件分发（事务内）+ 异步事件投递（RocketMQ，事务后） |
| PluginContainer | `com.api.lowcode.plugin` | 插件加载、隔离、生命周期、SPI 调度 |
| TransactionOrchestrator | `com.api.lowcode.tx` | 编程式事务编排，串联引擎+插件+事件 |

### 1.4 与低代码前端的契约

前端设计器产出的 Schema 中包含 `bizCode`（业务编码）与 `action`（操作类型：create/update/delete/submit/revoke/query）。运行时前端统一调用：

```
POST /api/lowcode/gateway
{
  "bizCode": "purchaseOrder",
  "action": "submit",
  "payload": { ... },          // 表单数据
  "context": { "tenantId": "...", "userId": "..." }
}
```

后台根据 `bizCode` 查 MetaRegistry 得到该业务的元数据配置，按 `action` 走对应执行器，整个过程**无需为每个业务写 Controller/Service**。

## 2. 通用后台引擎设计（配置驱动）

### 2.1 元数据配置模型

元数据是通用引擎的"图纸"，存储在数据库表中，可由"元数据配置页面"（本身也是低代码页面）维护，也可由设计器导出。

#### 2.1.1 核心配置表

```sql
-- 业务元数据主表
lc_biz_meta (
  id, bizCode, bizName, mainTable, mainTableAlias,
  statusField,          -- 状态字段名（示例；实际下达/撤销由任意字段变更事件定义，见第 13 章，非必须专用状态字段）
  logicDeleteField,     -- 逻辑删除字段
  tenantId, version, remark
)

-- 字段元数据
lc_field_meta (
  id, bizCode, fieldName, columnType, dataType,
  isRequired, isUnique, isSystemField,
  permissionExpr,       -- 字段级权限表达式
  defaultValueExpr,     -- 默认值（支持 SpEL/SQL）
  validationExpr,       -- 校验规则
  sortNo
)

-- 动作绑定（把 action 绑到执行策略）
lc_action_meta (
  id, bizCode, action,      -- create/update/delete/submit/revoke/query
  strategyType,             -- SINGLE/BATCH/IMPORT 等
  preHookPlugins,           -- 前置插件 ID 列表（JSON）
  postHookPlugins,          -- 后置插件 ID 列表（JSON）
  statusTransition,         -- 状态迁移定义（submit: DRAFT→APPROVED）
  dataScopeExpr,            -- 数据权限表达式
  enabled
)

-- 状态机定义
lc_state_machine (
  id, bizCode, currentState, nextState, event,
  guardExpr,              -- 守卫条件（SpEL）
  action,                 -- 触发该迁移的 action
  enabled
)
```

#### 2.1.2 元数据缓存

> **复用现有基础数据缓存**：平台已有基础数据缓存机制，元数据缓存、引用编码缓存、字典缓存等一律复用该机制，不单独设计缓存层。

- 启动时从 DB 加载全量 Meta 到内存（`MetaRegistry`），以 `bizCode` 为 key。
- 复用现有基础数据缓存（Redis + 本地缓存）作为分布式副本。
- 元数据变更发布 `META_CHANGED` 事件，各节点刷新本地缓存（通过 RocketMQ 广播 + 版本号比对）。

### 2.2 CRUD 通用执行流程

以 `action=create` 为例：

```
GenericGatewayController.handle(bizCode, action, payload)
  → MetaRegistry.getMeta(bizCode)            // 取元数据
  → TransactionOrchestrator.run(tx -> {      // 开启编程式事务
      1. PluginContainer.invokePreHooks(bizCode, action, ctx)   // 前置插件（事务内）
      2. CrudExecutor.execute(meta, action, ctx)                // 引擎执行 SQL
      3. StateMachine.transitionIfNeed(meta, action, ctx)       // 状态迁移（submit/revoke）
      4. EventBus.fireSync(stateChangeEvents)                   // 同步事件（事务内）
      5. PluginContainer.invokePostHooks(bizCode, action, ctx)  // 后置插件（事务内）
      6. EventBus.fireAsync(stateChangeEvents)                  // 异步事件入 MQ（事务后）
  })
```

> **关键**：步骤 1~5 全部在同一个 `PlatformTransactionManager` 编程式事务内，任一步抛异常则整体回滚；步骤 6 的 MQ 投递使用 **RocketMQ 事务消息**，确保 DB 提交与 MQ 投递的最终一致。

#### 2.2.1 CrudExecutor 内部能力

> **复用现有数据库引擎**：CrudExecutor 不重写 SQL 执行层，基于平台已有的数据库引擎构建（动态拼装 SQL 后交由现有引擎执行），复用其连接池、事务、方言能力。

- **动态 SQL 构建**：基于 FieldMeta 拼装 insert/update/delete/select，交由现有数据库引擎执行（如 MyBatis-Plus `SqlInjector` + 自定义 `AbstractMethod`，或 `SqlSession` 动态执行）。
- **字段权限**：按 `permissionExpr` 过滤可读/可写字段（结合当前用户上下文）。
- **数据权限**：按 `dataScopeExpr` 注入 WHERE 条件（部门/租户隔离）。
- **默认值/校验**：`defaultValueExpr`、`validationExpr` 支持 SpEL 与内置规则。
- **批量/导入**：`strategyType=BATCH/IMPORT` 时走批量执行器，复用同一事务。

### 2.3 下达/撤销状态机

下达（submit）与撤销（revoke）本质是状态迁移，由 `StateMachine` 统一处理：

```
状态机示例（采购单）：
  DRAFT --submit--> SUBMITTED --approve--> APPROVED --revoke--> DRAFT
```

- `StateMachine.transitionIfNeed` 依据 `lc_state_machine` 校验 `(currentState, action)` 是否存在合法迁移。
- 校验 `guardExpr`（SpEL，可调用插件提供的函数）。
- 迁移成功后更新 `statusField`，并产出 `StateChangeEvent`（含 fromState/toState/bizCode/businessId）。
- **撤销的特殊处理**：撤销可能需要"反向业务补偿"（如已扣减库存需回补），这通过**撤销专用插件钩子** `onRevoke` 实现，仍在同一事务内。

### 2.4 通用性的边界

- **能配置覆盖的**：标准 CRUD、字段权限、数据权限、状态流转、默认值/校验、简单业务规则（SpEL）。
- **需要插件的**：跨表复杂计算、调用外部系统、自定义校验逻辑、撤销补偿、审批流对接、报表生成等。
- 这条边界是本方案的核心：**配置解决 80% 通用场景，插件解决 20% 定制场景**，两者在同一事务内无缝衔接。

## 3. 插件机制设计（R3）

### 3.1 设计目标

1. 本地开发 → 打包 jar → 上传到平台 → 热加载生效，**全程不修改平台核心 jar**。
2. 插件之间隔离，避免类冲突；插件可依赖平台 SDK（提供 API 给插件用）。
3. 插件可注册到指定 `bizCode + action` 的前置/后置钩子，也可订阅事件。
4. 插件可被启用/禁用/卸载/升级，且支持版本管理。

### 3.2 插件 SPI 规范

平台定义一组 SPI 接口（位于 `com.api.lowcode.plugin.spi`），插件实现这些接口即可。

```java
// 插件主入口
public interface Plugin extends Lifecycle {
    String pluginId();
    String version();
    void init(PluginContext ctx);
}

// 动作钩子（前置/后置，事务内同步执行）
public interface ActionHook extends Plugin {
    @HookPhase Phase phase();              // PRE / POST
    boolean support(String bizCode, String action);
    void invoke(ActionContext ctx);        // 抛异常将回滚整事务
}

// 状态变化监听（事务内同步，可参与事务）
public interface StateChangeListener extends Plugin {
    boolean support(String bizCode, String event);
    void onStateChange(StateChangeEvent evt);  // 抛异常回滚
}

// 自定义函数（供 SpEL guardExpr/defaultValueExpr 调用）
public interface CustomFunction extends Plugin {
    String functionName();
    Object invoke(Map<String, Object> args);
}

// 校验器扩展
public interface CustomValidator extends Plugin {
    String validatorCode();
    void validate(ValidationContext ctx);
}
```

`PluginContext` 向插件暴露平台能力（受限 API）：

```java
public interface PluginContext {
    // 事务内 SQL 执行（复用当前事务）
    int insert(String bizCode, JSONObject data);
    int update(String bizCode, JSONObject data);
    JSONObject queryById(String bizCode, Object id);
    // 发起子业务动作（同事务内嵌套调用，复用事务）
    ActionResult invokeAction(String bizCode, String action, JSONObject payload);
    // 读取配置
    String getConfig(String key);
    // 日志（独立 traceId）
    PluginLogger logger();
    // 仅事务后可用的异步能力
    void sendAsync(String topic, Object payload);
}
```

> **重要约束**：`PluginContext` 的所有同步数据操作**强制复用当前事务**（通过 `TransactionSynchronizationManager` 绑定同一连接），从而满足 R5 的事务一致性。插件无法独立提交或回滚事务，只能通过抛异常触发整体回滚。

### 3.3 插件隔离与类加载器

采用 **"父子隔离 + SDK 共享"** 模型：

```
        PlatformClassLoader（加载平台核心 + SDK 接口）
              │
      ┌───────┴────────┐
      ▼                ▼
 PluginClassLoaderA   PluginClassLoaderB
  (插件A + 其依赖)     (插件B + 其依赖)
```

- 每个 `PluginClassLoader` 继承平台 ClassLoader，但**优先自己加载**插件本地依赖（child-first），仅将平台 SDK 接口与 JDK 类委托给父加载器。
- 这样插件 A、B 可分别携带不同版本的第三方库而互不影响。
- 卸载插件时置空其 ClassLoader 并 GC，释放资源。
- 使用 `fastjson2` 时注意：插件内 JSONObject 应通过平台 SDK 获取，避免类加载器差异导致类型转换异常（方案：SDK 统一用 `com.alibaba.fastjson2.JSONObject`，由父加载器加载）。

### 3.4 插件描述文件

每个插件 jar 根目录包含 `plugin.yml`：

```yaml
pluginId: purchase-order-plugin
version: 1.2.0
name: 采购单定制插件
author: xxx
minPlatformVersion: 1.0.0
entryClass: com.customer.plugin.PurchaseOrderPlugin
dependencies:                          # 插件级依赖（可选）
  - pluginId: base-rules-plugin
    version: ">=1.0.0"
permissions:                           # 向平台申请的能力
  - sql:purchaseOrder:rw
  - config:customKey
  - async:topic:orderEvent
hooks:
  - impl: com.customer.plugin.SubmitPreHook
  - impl: com.customer.plugin.RevokePostHook
listeners:
  - impl: com.customer.plugin.StockChangeListener
```

### 3.5 插件上传与热加载

```
上传 jar → 校验签名 & plugin.yml → 落盘 plugins/{pluginId}/{version}/xxx.jar
         → 注册到 lc_plugin_registry 表
         → PluginContainer.load(pluginId, version)
              → 新建 PluginClassLoader
              → 实例化 entryClass → init(ctx)
              → 注册 hooks/listeners 到调度表
         → 发布 PLUGIN_LOADED 事件（集群广播，各节点加载）
```

- **热加载**：通过新增 ClassLoader + 切换调度表引用实现，旧引用在当前请求处理完后被 GC，**不停机**。
- **卸载**：先从调度表摘除（新请求不再路由），等待在途请求完成（引用计数归零），再卸载 ClassLoader。
- 集群一致性：上传后通过 RocketMQ 广播 `PLUGIN_LOAD` 指令，各节点拉取 jar 并加载；加载结果回报协调节点，失败则回滚注册。

### 3.6 插件与配置的绑定关系

插件实现 `support(bizCode, action)` 自行声明适用范围，**无需修改 `lc_action_meta`**。但也可在 `lc_action_meta.preHookPlugins/postHookPlugins` 中显式指定插件顺序（用于多插件排序）。两者并存时：显式配置的插件按配置顺序先执行，自声明匹配的插件按注册顺序后执行。

## 4. 事件监听与状态变化捕捉（R4）

### 4.1 事件分类

| 类型 | 触发时机 | 执行方式 | 事务关系 |
|------|----------|----------|----------|
| `BEFORE_ACTION` | 引擎执行前 | 同步 | 事务内，可回滚 |
| `AFTER_ACTION` | 引擎执行后 | 同步 | 事务内，可回滚 |
| `STATE_CHANGE` | 状态迁移后 | 同步 + 异步 | 同步在事务内；异步事务后 |
| `DATA_CHANGED` | 数据变更后 | 异步 | 事务后（MQ） |
| `META_CHANGED` | 元数据变更 | 异步广播 | 事务后 |

### 4.2 事件总线设计

```java
public interface EventBus {
    // 同步分发（事务内，订阅者异常会抛出导致回滚）
    void fireSync(BizEvent event);
    // 异步分发（事务提交后投递 RocketMQ）
    void fireAsync(BizEvent event);
}
```

- **同步订阅**：实现 `StateChangeListener` 等同步 SPI 的插件，在 `fireSync` 时被调用，**与引擎、插件钩子同事务**。适合"状态变更后需在同事务内写关联表"的场景。
- **异步订阅**：事件序列化后通过 **RocketMQ 事务消息**投递。DB 提交 → MQ 半消息提交 → 消费者处理。适合"发通知、推下游系统、生成报表"等可异步、可重试的场景。

### 4.3 状态变化的捕捉点

`StateMachine.transitionIfNeed` 在状态字段实际更新前后产出事件：

```
BEFORE_STATE_CHANGE(from, to)  → 同步事件（可否决迁移：抛异常回滚）
  ↓ 状态字段 UPDATE
AFTER_STATE_CHANGE(from, to)   → 同步事件（事务内关联处理）
  ↓ 事务提交
STATE_CHANGE_ASYNC             → MQ 异步事件（下游消费）
```

### 4.4 订阅方式（配置 + 代码双轨）

1. **配置订阅**：在 `lc_event_subscription` 表配置 `(bizCode, event, handlerType, handlerConfig)`，`handlerType=NOTIFY/WEBHOOK/MQ_TOPIC`，由平台内置处理器执行。无需写代码。
2. **代码订阅**：插件实现 `StateChangeListener`，由 PluginContainer 注册。可写任意业务逻辑。

两种订阅均在事件总线统一调度，顺序：同步代码订阅 → 同步配置订阅 →（事务提交后）异步配置订阅 → 异步代码订阅。

## 5. 事务一致性方案（R5）

### 5.1 问题本质

R3 的插件钩子与 R4 的状态事件监听，若各自管理事务或独立调用，会出现：
- 插件提交了但引擎回滚 → 脏数据。
- 引擎提交了但事件监听抛异常 → 状态已变但关联数据未写。
- 跨方法调用，Spring AOP 声明式事务无法正确传播。

### 5.2 解决方案：编程式事务统一编排

`TransactionOrchestrator` 使用 `PlatformTransactionManager` 的编程式 API，**单一事务边界**包裹全部步骤：

```java
public class TransactionOrchestrator {
    private final PlatformTransactionManager txManager;

    public ActionResult run(String bizCode, String action, ActionContext ctx, Action body) {
        TransactionDefinition def = new DefaultTransactionDefinition(
            TransactionDefinition.PROPAGATION_REQUIRES_NEW);   // 或 REQUIRED
        ((DefaultTransactionDefinition) def).setTimeout(txTimeout);
        TransactionStatus status = txManager.getTransaction(def);
        try {
            ActionResult r = body.execute(ctx);                 // 引擎+插件+同步事件 全在此
            txManager.commit(status);
            // 提交成功后才投递异步事件（RocketMQ 事务消息的本地事务已 commit）
            return r;
        } catch (Throwable e) {
            txManager.rollback(status);
            throw e;
        }
    }
}
```

- **插件与事件复用当前事务**：`PluginContext` 的 SQL 操作通过 `TransactionSynchronizationManager.getResource(dataSource)` 拿到当前连接，确保同连接同事务。
- **禁止插件自开事务**：SDK 不暴露独立事务 API；插件若调用 `invokeAction` 触发子业务，子业务以 `PROPAGATION_REQUIRED` 加入当前事务（嵌套调用复用同一物理事务）。
- **异步事件最终一致**：使用 RocketMQ 事务消息，`fireAsync` 实为发送半消息，本地事务即上述 DB 事务；DB 提交 → 半消息 commit；DB 回滚 → 半消息 rollback。消费端幂等处理。

### 5.3 事务边界图

```
┌──────────── 编程式事务 BEGIN ────────────┐
│  前置插件钩子（ActionHook PRE）            │
│  CrudExecutor.execute                     │
│  StateMachine.transition + 同步事件       │
│  同步 StateChangeListener（插件）         │
│  后置插件钩子（ActionHook POST）           │
│  —— 以上任一异常 → 整体 ROLLBACK ——       │
└──────────── COMMIT ──────────────────────┘
        │
        ▼ （RocketMQ 事务消息 commit）
   异步事件投递 → 下游消费（最终一致）
```

### 5.4 异常与回滚策略

- **业务异常**：插件抛 `BizException`，引擎回滚，前端收到结构化错误码。
- **系统异常**：`RuntimeException` 触发回滚；受检异常在编排层包装为运行时异常。
- **异步事件失败**：MQ 消费失败走 RocketMQ 重试 + 死信队列，不影响已提交的主事务（最终一致，需消费端幂等）。
- **超时**：事务超时由 `lc_action_meta` 可配置，默认 30s。

### 5.5 分布式事务的取舍

- 本方案**不引入 Seata/2PC**，理由：插件与引擎在同一 JVM 同一数据源，单库本地事务即可保证强一致；跨系统调用走 MQ 事务消息保证最终一致，复杂度与性能更优。
- 若未来出现"插件内跨库写"需求，再针对该插件引入 Seata AT 模式，作为插件的可选依赖，不污染平台核心。

## 6. 本地开发与调试方案（R6）

### 6.0 先搞懂：代码到底在哪里执行（关键认知）

> 常见误解："本地启动插件，请求就会到我本地。" **不是这样。** 插件不是独立服务，不能"本地启动着等请求来"。代码只会在两个地方执行：

| | 代码在哪执行 | 请求从哪发起 | 断点怎么命中 | 平台参与吗 |
|---|---|---|---|---|
| **方式1 纯本地** | 你本地 JVM | 本地 JUnit 测试代码 | 本地 JVM 跑本地代码，IDEA 直接命中 | **不参与** |
| **方式2 远程联调** | 平台 JVM（你的代码被推送上去） | 真实前端发到平台 | 平台执行你的代码，通过 JDWP 把断点状态发回本地 IDEA | 参与 |

**方式2 里你的代码不在本地跑，是被推送到平台 JVM 里跑，本地 IDEA 只是通过调试协议"看"断点。** 这才是"远程联调"。

#### 举例：插件有 bug，两种方式走一遍

**方式1（纯本地，平台不参与）**：
```
IDEA 写 JUnit：harness.fireAction("purchaseOrder","create",payload)
  → 在你本地 JVM 执行你的插件代码，连本地开发库
  → 断点直接命中（本地 JVM 跑本地代码）
  → 请求从没发到平台，平台不知道、不参与
```

**方式2（远程联调，请求发平台但用你的代码）**：
```
1. dev-agent 把插件代码推送到平台 JVM（你的 class 加载到平台），标记 isDebug+debugUserId=你
2. 你登录平台点保存 → 请求发到平台
3. 平台判断：是你的请求 → 用调试版（你的代码）执行；别人 → 用正式版
4. 平台 JVM 执行你的代码 → 命中断点 → JDWP 把断点/变量发回本地 IDEA
5. 你在本地 IDEA 看到断点、单步（代码实际在平台 JVM 跑）
```

#### 回答两个常见疑问

- **"平台怎么知道用我本地还是平台原有的插件？"**：方式1 平台不需要知道（请求没发给平台）；方式2 平台靠 `isDebug+debugUserId` 标记判断。
- **"我本地启动了就会到我本地吗？"**：不会。本地启动的是 IDEA/测试进程，不是插件服务。方式1 请求是本地测试发起的在本地执行；方式2 请求发平台、代码在平台执行、断点连回本地看。

### 6.1 一句话理解

**插件就是一个普通的 Java Maven 项目**：依赖平台发布的 SDK jar，实现几个接口，打包成 jar 上传。本地能用 JUnit 测试、能在 IDEA 打断点，**不需要启动整个平台**就能开发调试。

平台提供两个 jar（发布到内部 Maven 仓）：
- `lowcode-plugin-sdk`：SPI 接口 + `PluginContext`（运行时由平台实现，本地由 `LocalPluginContext` 模拟）
- `lowcode-plugin-test`：`PluginTestHarness` 测试夹具，本地模拟平台调度插件

### 6.3 第二步：写插件类（实现 SPI）

场景：保存采购单前，校验金额>0 且供应商存在（同事务内查关联表）。

```java
package com.customer.plugin;

import com.api.lowcode.plugin.spi.ActionHook;
import com.api.lowcode.plugin.spi.HookPhase;
import com.api.lowcode.plugin.context.ActionContext;
import com.api.lowcode.plugin.context.PluginContext;
import com.api.lowcode.plugin.exception.BizException;
import com.alibaba.fastjson2.JSONObject;

public class PurchaseOrderSavePreHook implements ActionHook {

    @Override
    public String pluginId() { return "purchase-order-plugin"; }

    @Override
    public HookPhase phase() { return HookPhase.PRE; }   // 前置钩子（保存前）

    @Override
    public boolean support(String bizCode, String action) {
        // 声明本插件只处理 采购单的 create/update
        return "purchaseOrder".equals(bizCode)
            && ("create".equals(action) || "update".equals(action));
    }

    @Override
    public void invoke(ActionContext ctx) {
        JSONObject payload = ctx.getPayload();
        PluginContext p = ctx.getPluginContext();

        Double amount = payload.getDouble("amount");
        if (amount == null || amount <= 0) {
            throw new BizException("PO_AMOUNT_INVALID", "采购金额必须大于0");
        }

        // 同事务内查供应商（复用当前事务，不另开连接）
        String supplierId = payload.getString("supplierId");
        JSONObject supplier = p.queryById("supplier", supplierId);
        if (supplier == null) {
            throw new BizException("SUPPLIER_NOT_FOUND", "供应商不存在: " + supplierId);
        }
        if ("DISABLED".equals(supplier.getString("status"))) {
            throw new BizException("SUPPLIER_DISABLED", "供应商已停用");
        }

        p.logger().info("采购单校验通过, supplier={}", supplierId);
        // 抛异常 → 整个保存事务回滚（R5）
    }
}
```

### 6.5 第四步：本地单元测试（不需要启动平台）

`PluginTestHarness` 直连本地开发库，模拟平台调度你的插件。**这就是"本地开发测试"**——在 IDEA 里右键跑测试，可在插件代码任意行打断点。

#### 6.5.1 测试数据从哪来（关键）

测试里的 `payload` 不用手编，四种来源，**推荐第 1 种**：

| 来源 | 怎么做 | 适合 |
|------|--------|------|
| **① 从真实请求抓（推荐）** | 测试环境平台正常操作一次 → F12 Network 复制 `/api/lowcode/gateway` 请求 payload → 存 `src/test/resources/fixtures/po_create.json` | 数据真实、字段全，调试已有业务插件 |
| ② 从数据库查 | `harness.queryById("purchaseOrder","PO001")` 拿真实记录改 | 测 update 插件 |
| ③ 手写 | `JSONObject.of("amount",100.0,"supplierId","S001")` | 字段少、逻辑简单 |
| ④ SDK 按 Meta 自动生成 | `MockDataBuilder.byMeta("purchaseOrder")` 自动填充默认值 | 快速构造，但数据是假的 |

**① 的操作**：在测试环境平台新建采购单填好字段点保存 → F12 → Network → 找到 gateway 请求 → 复制 Request Payload → 存 JSON 文件。一次抓取反复用，改测试场景只覆盖几个字段。

### 6.7 第六步：远程联调（平台跑真实引擎，本地断点）

本地测试只验证插件逻辑，没经过真实引擎/状态机/事件。要验证插件在真实平台下的行为：

**原理**：远程平台 JVM 开 JDWP 调试端口，本地 IDEA 用 "Remote JVM Debug" 连上去，在本地源码打断点，就能命中运行在远程平台的插件代码。

**步骤**：
1. 远程开发平台 JVM 启动参数加：
   `-agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=5005`
2. 把你的插件 jar 上传到开发平台（或用 dev-agent 推送，见 6.8）
3. IDEA → Run → Edit Configurations → + → Remote JVM Debug → Host 填平台 IP、Port 填 5005
4. 在本地插件源码 `invoke` 里打断点
5. 触发业务操作（前端下单）→ 平台执行你的插件 → **命中本地 IDEA 断点**，可单步、看远程变量
6. 改代码后：重新打包上传（或 dev-agent 自动推送）→ 重新触发 → 调试新代码

> 行号一致是关键：本地源码与远程加载的 class 必须同版本编译，断点才能对上。

### 6.8 dev-agent：改代码自动推送到远程平台（可选，更顺）

`lowcode-dev-agent`（IDEA 插件或 CLI）免去手动打包上传：

```
本地改代码 → dev-agent 监听到 class 变更（或手动触发）
  → 自动编译 + 推送 class 到远程开发平台
  → 平台以"调试版"热加载（标记 isDebug=true，绑定你的 debugUserId）
  → 只有你的请求路由到调试版，不影响他人
  → 日志/异常栈通过长连接回传 IDEA
```

配合 JDWP，实现"改代码 → 自动生效 → 断点调试"的闭环。

### 6.9 三种调试模式对比

| 模式 | 怎么跑 | 能断点吗 | 验证范围 | 需本地部署平台吗 | 适用 |
|------|--------|----------|----------|------------------|------|
| **A 纯本地测试** | JUnit + 本地开发库 | 能（IDEA 直接断点） | 仅插件逻辑 | 不需要 | 插件逻辑开发，最快 |
| **B 远程联调** | 平台跑 + IDEA Remote Debug 连 JDWP | 能（命中远程执行） | 插件+真实引擎+事件 | 不需要 | 集成联调 |
| **C 本地起全套** | 本地前端+本地后端+本地库，插件加载本地 class | 能（直接命中） | 全链路 | **需要** | 要前端+数据全在本地 |

### 6.9.1 方式3：本地起完整平台（前端+数据全在本地）

> 用户需求：要有前端、请求和数据都在本地环境。**此方式需在本地部署平台程序**，但换来最完整的本地调试体验：前端点按钮→本地后端执行你的插件→本地库→IDEA 断点直接命中。

#### 架构

```
本地前端(npm run dev) → 本地后端平台(SpringBoot) → 加载你的插件(本地 target/classes) → 本地数据库
                                                                       ↓
                                                             IDEA 断点直接命中（都在本地 JVM）
```

#### 搭建步骤

> **为什么中间件也是硬依赖？** 后端平台启动时会连 MySQL/Redis/RocketMQ，连不上就起不来或运行报错：MySQL 存业务数据+元数据+插件注册表（CRUD 读写库）；Redis 是基础数据缓存+元数据缓存副本+会话；RocketMQ 投递异步事件（字段变更事件、插件加载广播、元数据变更广播）。前端后端是"演员"，中间件是"舞台灯光音响"，缺一不可。但不用一个个装，Docker 一键起即可。

| 步 | 做什么 | 命令/说明 |
|----|--------|----------|
| 1 | 本地装中间件 | MySQL、Redis、RocketMQ（建议 Docker 一键起：`docker compose up -d`，用完 `docker compose down` 清） |
| 2 | 拉平台后端代码 | `git clone <平台后端仓>` → 配 `application-local.yml` 指向本地库/Redis/MQ |
| 3 | 启动本地后端 | `mvn spring-boot:run -Dspring.profiles.active=local` |
| 4 | 配置插件加载方式 | 平台配置 `plugin.loadMode=file`，`plugin.file.path=你的插件项目/target/classes` |
| 5 | 启动本地前端 | `npm run dev`，`.env.development` 指向本地后端 `localhost:8080` |
| 6 | 调试 | IDEA 插件代码打断点 → 本地前端点保存按钮 → 本地后端执行插件 → **断点直接命中** |

#### 关键优势

- **插件不用打包上传**：平台以 `file://` 直接加载你本地编译的 `target/classes`，改代码 → IDEA Build → 平台热重载 → 再点按钮测新代码。
- **断点直接命中**：全在本地 JVM，不需要 JDWP 远程调试协议。
- **数据全在本地**：本地库随便造数据、随便改、随便回滚，不污染他人。
- **完整链路**：前端→后端引擎→状态机→事件→插件，全链路可断点。

#### 代价

- 本地需部署平台程序：前端 + 后端 + MySQL + Redis + RocketMQ。
- 首次搭建环境耗时，但搭好后日常调试体验最好。

#### 与方式2 的取舍

| | 方式2 远程联调 | **方式3 本地起全套** |
|---|---|---|
| 前端 | 远程平台已部署的 | **本地前端** |
| 后端/数据 | 远程平台 | **本地** |
| 需本地部署平台 | 不需要 | **需要** |
| 插件代码 | 推送到远程 JVM | **本地 JVM 直接加载** |
| 断点 | JDWP 连回本地 | **直接命中** |
| 调试速度 | 稍慢（网络） | **最快** |
| 适合 | 本地不想装平台 | **要前端+数据全在本地** |

#### 变体：本地后端连测试环境中间件（省去本地安装）

> 本地后端的 `application-local.yml` 配测试环境的 MySQL/Redis/MQ 地址，启动就连测试环境中间件，**本地不用装任何中间件**。但有风险需权衡。

| 中间件 | 直连风险 | 严重度 |
|--------|---------|--------|
| MySQL | 本地写操作直接写测试库，污染测试数据影响他人 | 高 |
| RocketMQ | 本地发的消息可能被测试环境消费者消费，触发连锁 | 中高 |
| Redis | 写缓存键可能覆盖测试环境缓存，影响小可清 | 低 |

**建议**：
- 只读/查数据 → 直连测试库安全
- 要写操作 → **别直连测试主库**，用独立调试库（测试环境开个独立 database 如 `lowcode_dev_xxx`，本地连测试 MySQL 但用这个库，数据隔离）
- Redis/MQ 连测试影响小可连；MQ 用独立 topic 或本地禁用异步投递，避免测试消费者消费你的消息

| 方案 | 本地要装啥 | 数据污染 | 适合 |
|------|-----------|---------|------|
| 本地 Docker 全装 | Docker 起三个 | 无（全隔离） | 要完全隔离、随便造数据 |
| **连测试中间件+独立调试库** | **啥都不装** | 无（独立库隔离） | **多人共用测试环境，最推荐** |
| 直连测试主库 | 啥都不装 | 高（污染他人） | 测试环境你独占 |

**推荐日常**：方式 A 写插件逻辑 → 方式3（或方式2）联调 → 部署开发环境验证。

### 6.9.2 更简单的本地调试方案（不想装中间件时）

> 用户觉得方式3 全装中间件太重。以下两个方案更简单。

#### 方案A：嵌入式降级（零中间件，最简单的"全套本地"）

后端配 `local` profile，用嵌入式组件替代真实中间件：

| 真实中间件 | 本地替代 | 说明 |
|-----------|---------|------|
| MySQL | H2 内存库（`MODE=MySQL`） | 启动自动建表，零安装 |
| Redis | 嵌入式 Redis 或 Caffeine 进程内缓存 | 零安装 |
| RocketMQ | 禁用异步事件（local profile 关闭 MQ 投递） | 异步事件本地不测 |

```yaml
# application-local.yml
spring:
  datasource:
    url: jdbc:h2:mem:lowcode_dev;MODE=MySQL
lowcode:
  cache: caffeine
  async-event: disabled
```

启动：`mvn spring-boot:run -Dspring.profiles.active=local` + `npm run dev`，**零中间件，只起前后端**。

- 优点：最简单，本地啥都不装，一条命令起
- 缺点：H2 与 MySQL 有 SQL 语法差异（复杂 SQL 可能本地过、环境报错）；异步事件测不了
- A适合：调试插件同步逻辑 + 前端交互；不适合调试异步事件/复杂 SQL

#### 方案B：方式2 远程联调（最简单，但非"全套本地"）

本地只装 IDEA + 插件项目，平台用测试环境的，dev-agent 推插件 + JDWP 断点。本地啥都不装，但数据/前端在远程。

#### 简单程度排序

| 方案 | 本地装啥 | 全套本地 | 取舍 |
|------|---------|---------|------|
| 方式2 远程联调 | 只 IDEA+插件项目 | 否 | 最简单，但数据在远程 |
| **方案A 嵌入式降级** | 只起前后端，零中间件 | 是 | 最简单的全套本地，H2/MQ 失真 |
| 连测试中间件+独立库 | 起前后端，连测试中间件 | 是 | 不装中间件，数据隔离 |
| 方式3 Docker 全装 | 全装 | 是 | 最重但最真实 |

**务实建议**：日常用方案A 快速本地调试插件+前端，碰到 H2 不兼容的 SQL 或要测异步事件时再切测试环境验证。不必为"全套本地真实"天天扛 Docker。

### 6.9.3 参考：金蝶苍穹的本地开发调试做法

> 金蝶苍穹（Kingdee Cosmic）是成熟企业级 PaaS，其本地调试方式印证了本方案思路。

#### 苍穹的做法

| 环节 | 苍穹 |
|------|------|
| 元数据驱动 | 苍穹开发工具可视化设计单据元数据，后端通用框架按元数据执行 CRUD |
| 插件扩展 | Java 插件实现 `OperationPlugIn`/`BillPlugIn`/`FormPlugin`，编译 jar 注册，不修改平台核心 |
| **本地调试** | **本地开发服务**（轻量运行时）：本地启动 → 连**开发环境**的数据库和中间件（不本地装）→ 本地加载插件 class → 前端用**开发环境**的苍穹 Web 客户端，API 代理到本地服务 → 触发插件 → 本地执行 → IDE 断点命中 → 改代码热重载 |
| 环境隔离 | 开发/测试/生产隔离，本地连开发环境 |

**关键**：苍穹开发者本地**不装 MySQL/Redis/MQ**，本地起轻量运行时连开发环境中间件，前端用开发环境的代理到本地。这正是本方案"方式3 变体 / 方式2"的工程化封装。

#### 苍穹 vs 本方案

| 维度 | 苍穹 | 本方案 |
|------|------|--------|
| 元数据驱动 | 苍穹开发工具设计元数据 | `lc_biz_meta` 配置驱动 |
| 插件扩展 | `OperationPlugIn` 等 | `ActionHook` 等 SPI |
| 本地调试 | 本地轻量运行时 + 连开发环境中间件 + 前端代理到本地 | 方式3 变体 / 方式2 |
| 不改平台 | 插件不侵入核心 | 同 |
| 事务 | 苍穹事务管理，插件同事务 | 编程式事务编排 |

#### 印证与借鉴

1. 本方案与成熟 PaaS 思路一致（元数据驱动 + 插件扩展 + 不侵入平台 + 同事务）
2. **"连开发环境中间件 + 本地轻量运行时"是业界成熟做法**，不必本地装全套中间件
3. 前端用开发环境的 + API 代理到本地，比本地起前端更轻
4. **可借鉴**：做一个"本地开发服务"——比完整平台轻的运行时，专为本地调试，连开发环境中间件，加载本地插件 class，前端用开发环境的代理过来。即方式2/方式3变体的产品化封装，最终最舒服的本地开发体验。

#### 元数据驱动：苍穹 vs 本方案的区别与可借鉴点

| 维度 | 苍穹 | 本方案 | 差距 |
|------|------|--------|------|
| **元数据分层继承** | 产品层/行业层/客户层，上层继承+扩展+覆盖下层，不改下层 | 单层配置，扩展靠插件（只改行为不改结构） | **最大差距** |
| 元数据范围 | 一切皆元数据（业务对象/字段/操作/表单/列表/报表/流程/权限） | 偏窄（页面 schema + CRUD/状态机/事件） | 中 |
| 元数据版本化 | 有版本，产品升级时客户扩展自动兼容 | 未设计 | 中 |
| 应用包 | 元数据+插件+配置打包，整体部署/迁移/升级 | 插件 jar 单传，元数据单配 | 中 |
| 动态建表 | 按元数据动态建表/改表，设计时校验 | 有，但字段非法跳过建表且前端显示成功（已知 bug） | 小（要修） |
| 元数据与代码分离 | 元数据描述结构，插件描述行为 | 一致 | 无 |

**最关键差距——元数据分层继承**：苍穹靠产品层/行业层/客户层分层，客户加字段/改属性都不碰标准产品，运行时三层合并。本方案单层配置，"加字段"要么改平台元数据（侵入）要么靠插件（只改行为不改结构），**结构层扩展缺机制**。

**可借鉴点（按价值排序）**：
1. **元数据分层继承（最值得学）**：`lc_biz_meta` 加 `layer`（PLATFORM/INDUSTRY/CUSTOMER）+ `parentMetaId`，运行时按层合并。与插件互补——插件改行为，分层改结构。这样"加一个字段"也不改平台。
2. **元数据范围统一**：权限/流程/报表/列表也纳入元数据统一管理，运行时统一驱动。
3. **元数据版本化**：元数据带版本，平台升级时客户扩展自动兼容（补第 14 章 F1）。
4. **应用包**：一个业务的元数据+插件+权限+流程打包，整体部署/迁移/升级。
5. **动态建表校验前置**：设计时校验字段合法性，建表失败必须反馈前端（对应"后端失败透传前端"约束）。

**不必全盘照搬**：苍穹是重平台（专门开发工具+完整分层+多年积累），本方案是轻量低代码。必学：分层继承、建表校验前置；按需学：元数据范围统一、版本化、应用包；不必学：苍穹重客户端开发工具。

### 6.10 远程联调如何定位到具体页面/请求（实操关键）

> 平台上有无数页面、多用户同时在用，远程联调时怎么确保断点只命中"我要调试的那个页面的那次请求"，不被其他页面/用户干扰？分两层解决。

#### 6.10.1 定位：插件本身就绑定了具体页面/业务

插件代码里 `support(bizCode, action)` 已写死处理哪个业务，`bizCode` 是页面/业务的唯一标识。**你开发时就知道是给哪个 bizCode 写的插件，不存在"不知道调试哪个页面"。**

确认某页面对应哪个 bizCode 的方式：
- 设计器/页面管理里看该页面的 bizCode（页面保存时已绑定）
- 或浏览器打开页面，F12 看网关请求体里的 `bizCode` 字段
- 或平台提供"页面 ↔ bizCode ↔ 插件"映射查询界面

#### 6.10.2 隔离：调试版插件只命中你的请求（关键）

多用户多页面同时在跑，直接断点会命中任何人的请求。解决：**调试版插件绑定 debugUserId（或 debugTag），只有你的请求路由到调试版命中断点，其他人走正式版不受影响。**

```
dev-agent 推送调试插件时标记 isDebug=true + debugUserId=你的账号
  ↓
平台调度时判断：
  · 请求 userId == debugUserId 且 bizCode 匹配 → 路由到调试版（命中本地断点）
  · 否则 → 路由到正式版（不断点，不影响他人）
```

操作流程：
1. 本地 IDEA 连上远程 JDWP，在插件代码打断点
2. 用**自己账号**登录平台 → 找到目标页面（按 bizCode/页面名）→ 操作
3. 你的请求命中调试版 → 命中本地断点，可单步调试
4. 其他用户同一页面的操作走正式版，互不干扰

> debugTag 方式更精细：dev-agent 给你的浏览器注入一个调试 Header/Cookie，带唯一 debugTag，平台按 tag 路由，连"同一账号的非调试请求"都不打断点。适合多人共用开发账号时。

#### 6.10.3 一句话总结

**你开发插件时就明确是给哪个 bizCode（页面/业务）写的**；远程联调时调试版插件绑定你的 userId/debugTag，只有你触发那个页面才命中断点，平台上其他无数页面和其他用户完全不受影响。

### 6.11 调试安全

- 远程 JDWP 端口仅开发网络/VPN 开放，生产禁用。
- 调试版插件（isDebug=true）不可上生产，上传时校验拒绝。
- dev-agent 长连接需开发令牌鉴权，定期轮换。

## 7. 多角色可行性评估

> 以下由 6 个角色独立评估，给出结论与风险。

### 7.1 架构师评估

**结论：可行，架构合理。**

- 配置驱动 + 插件 SPI 是低代码平台的主流范式（参考宜搭、简道云、泛微等），方向正确。
- 编程式事务统一编排避免了 AOP 声明式事务在嵌套调用下的传播陷阱，是 R5 的正确解法。
- 插件 ClassLoader 隔离采用 child-first，成熟方案（参考 Tomcat WebappClassLoader 思路），可行。
- **风险**：插件热加载的内存泄漏（旧 ClassLoader 无法 GC）需重点防范；建议设置卸载后的引用计数检查与监控。
- **建议**：元数据配置与插件绑定关系要文档化，避免"配置散落 + 插件隐式声明"导致行为难追溯。

### 7.2 后端工程师评估

**结论：可行，工作量集中在引擎与 SDK。**

- Spring Boot 2.3.12 + Spring 5.2.15 完全支持 `PlatformTransactionManager` 编程式事务、`TransactionSynchronizationManager`，无版本障碍。
- MyBatis-Plus 动态 SQL 注入可行；若不想侵入 MyBatis-Plus，也可用 `SqlSession` 直接执行动态 SQL。
- fastjson2 作为 Schema/事件序列化无问题；注意插件 ClassLoader 下 JSONObject 类型一致（由父加载器加载）。
- RocketMQ 4.9.8 支持事务消息，满足异步事件最终一致。
- **风险**：通用 CRUD 的动态 SQL 性能需压测；复杂查询（多表 join）配置化难度大，建议复杂查询仍走插件或视图。
- **建议**：`PluginContext` API 要克制，暴露过多会让插件与平台强耦合，失去隔离意义。

### 7.3 前端工程师评估

**结论：可行，契约清晰即可。**

- 前端只需保证设计器产出的 Schema 含 `bizCode + action`，运行时统一调 `/api/lowcode/gateway`，与现有低代码前端契合。
- 下达/撤销在前端表现为按钮 → action，无需特殊接入。
- 插件对前端透明（除非插件要扩展前端组件，那是另一条扩展轴，本期不覆盖）。
- **风险**：通用网关返回结构需标准化（成功/失败/字段错误/状态错误），前端要有统一处理。
- **建议**：网关响应规范先行，前端再做适配。

### 7.4 DBA 评估

**结论：可行，但需规范护航。**

- 元数据表设计合理，索引建议：`lc_biz_meta(bizCode)`、`lc_action_meta(bizCode,action)`、`lc_state_machine(bizCode,currentState,event)` 唯一索引。
- 通用 CRUD 的动态 SQL 需防注入：所有字段走预编译参数，表名/字段名走白名单（来自 Meta，非用户输入）。
- 状态字段更新需乐观锁（`version` 字段），防止并发下达。
- **风险**：元数据缓存与 DB 不一致的窗口需可控（依赖版本号比对）。
- **建议**：提供元数据变更审计日志；高频业务的 `lc_field_meta` 查询走内存缓存而非 DB。

### 7.5 运维评估

**结论：可行，需补监控与发布规范。**

- 插件 jar 上传需走制品库（Nexus）+ 签名校验，禁止裸 jar 直传生产。
- 热加载在集群下需保证最终一致：上传 → 广播 → 各节点加载结果回报，失败节点自动摘流或重试。
- Windows 部署（用户环境）下，JDWP 与 WebSocket 调试通道需在开发环境开放，生产关闭。
- **风险**：插件导致平台 OOM/线程泄漏会影响全局，需隔离资源（线程池上限、内存配额）。
- **建议**：插件加载/卸载、事务回滚、事件失败均接入监控（Prometheus + Grafana），关键指标：插件加载耗时、事务回滚率、MQ 消费延迟。

### 7.6 安全评估

**结论：可行，但插件是最大攻击面，需重点加固。**

- 插件代码来自客户本地开发，等同不可信代码，需在**沙箱**内运行：限制文件/网络/反射权限（通过 `SecurityManager` 或 Java 模块化隔离，JDK8 下用 SecurityManager + 自定义 Policy）。
- 插件权限声明（`plugin.yml.permissions`）需平台审批，最小授权。
- 上传 jar 签名校验，防篡改。
- `PluginContext` 不暴露底层 DataSource/SqlSession，仅暴露受限 API。
- **风险**：JDK8 的 SecurityManager 已弱化且性能有损；若用 JDK11+ 可考虑 Module + 自定义 ClassLoader 限制。
- **建议**：插件源码审计流程；高危插件（含网络/文件权限）需人工复核。

### 7.7 评估汇总

| 角色 | 结论 | 主要风险 |
|------|------|----------|
| 架构师 | 可行 | 热加载内存泄漏 |
| 后端 | 可行 | 动态 SQL 性能、复杂查询 |
| 前端 | 可行 | 网关响应规范 |
| DBA | 可行 | 注入防护、并发状态 |
| 运维 | 可行 | 集群一致性、资源隔离 |
| 安全 | 可行（需加固） | 插件沙箱、权限审批 |

**总体结论：方案可行，关键风险均有对应缓解措施，可进入开发。**

## 12. 微服务架构下的插件一致性（补充设计）

> 本章是对前文（偏单库单服务假设）的补充。用户环境为微服务架构，插件一致性是必须正面解决的问题。

### 12.1 问题背景

原方案 P0~P6 的事务一致性（R5）建立在"插件与引擎在同一 JVM 同一数据源"之上。微服务架构下该假设不再普遍成立，需额外解决：

| 编号 | 挑战 | 本质 |
|------|------|------|
| C1 | 多实例一致 | 同一服务的 N 个副本必须加载同一版本插件，否则行为分裂、请求结果不确定 |
| C2 | 跨服务分发 | 插件 jar 要可靠分发到所有目标服务实例，不能漏节点 |
| C3 | 版本屏障 | 加载是分阶段的，对外服务期间不能出现"部分实例新版本 + 部分旧版本" |
| C4 | 跨服务事务 | 插件 A 在服务1、插件 B 在服务2 时，R5 的事务一致性如何保证 |
| C5 | 元数据一致 | 多服务共享元数据，各服务本地缓存不能漂移 |
| C6 | 故障自愈 | 实例宕机/网络分区后，插件状态如何恢复并对齐 |

### 12.2 整体拓扑

```
                ┌──────────────────────────┐
                │   插件注册中心            │
                │  PluginRegistryCenter    │
                │  (独立服务/复用配置中心)   │
                └───────┬──────────┬───────┘
       上传/查询/编排     │          │ 心跳上报插件版本
                        ▼          ▼
                ┌──────────────────────────┐
                │   对象存储 (MinIO/OSS)    │  ← jar 制品库
                └──────────────────────────┘
                        ▲
   RocketMQ 广播         │ 拉取 jar
   PLUGIN_LOAD/UNLOAD    │
        ┌───────────────┼───────────────┐
        ▼               ▼               ▼
   ┌─────────┐     ┌─────────┐     ┌─────────┐
   │ 服务A-1  │     │ 服务A-2  │     │ 服务B-1  │  ...各微服务实例
   │PluginAgent│   │PluginAgent│   │PluginAgent│
   └─────────┘     └─────────┘     └─────────┘
```

每个微服务实例内嵌一个 `PluginAgent`，负责：向注册中心上报本实例已加载插件版本、接收加载/卸载指令、拉取 jar、调用本地 `PluginContainer` 加载、回报结果。

### 12.3 插件注册中心

#### 12.3.1 职责

- 插件元信息管理（pluginId、version、jarUrl、签名、minPlatformVersion、targetServices、status）
- 版本管理与发布编排（上传、审核、灰度、全量、回滚）
- 分发指令下发（通过 RocketMQ 广播 + 各实例拉取）
- 加载结果聚合与一致性判定（版本屏障）
- 各实例心跳与健康检查（实例上报当前插件版本集合，注册中心比对）
- 鉴权与签名校验

#### 12.3.2 核心数据模型

```sql
lc_plugin_release (
  id, pluginId, version, jarUrl, signature,
  minPlatformVersion, targetServices,   -- JSON: ["order-service","stock-service"]
  status,                               -- DRAFT/APPROVING/RELEASING/ACTIVE/ROLLBACK
  releaseStrategy,                      -- FULL/CANARY
  canaryInstances,                      -- 灰度实例列表
  createTime, creator
)

lc_plugin_load_record (
  id, releaseId, instanceId, serviceName,
  loadStatus,                           -- LOADING/SUCCESS/FAILED
  loadedVersion,                        -- 实际加载版本
  reportTime, errorMsg
)

lc_plugin_instance_heartbeat (
  id, instanceId, serviceName,
  loadedPlugins,                        -- JSON: [{pluginId,version}]
  lastHeartbeatTime, status             -- ONLINE/OFFLINE
)
```

#### 12.3.3 关键 API

```
POST /plugin/registry/upload          上传 jar（落对象存储 + 记录 release）
POST /plugin/registry/release         发起发布（指定 strategy、targetInstances）
GET  /plugin/registry/needed          服务启动时查询本服务应加载的插件列表
POST /plugin/registry/report          实例回报加载结果
GET  /plugin/registry/status          查询发布一致性状态
POST /plugin/registry/rollback        回滚到指定版本
```

### 12.4 插件分发与加载流程（两阶段生效）

```
[发起发布 release(v1.2.0, target=order-service 全量)]
   │
   ▼ 1. 注册中心：release.status = RELEASING，写入 lc_plugin_load_record(每实例一条 LOADING)
   │
   ▼ 2. RocketMQ 广播 PLUGIN_LOAD{pluginId, version, jarUrl, targetInstances}
   │
   ▼ 3. 各目标实例 PluginAgent 收到指令：
   │      a. 下载 jar → 校验签名 → 校验 minPlatformVersion
   │      b. 调用本地 PluginContainer.load()（新 ClassLoader，先不接入调度）
   │      c. 回报注册中心：SUCCESS / FAILED + errorMsg
   │
   ▼ 4. 注册中心聚合结果：
   │      - 全部 SUCCESS → 进入"切换阶段"：广播 PLUGIN_ACTIVATE{pluginId, version}
   │        各实例把调度表引用切到新版本，旧版本引用计数归零后卸载
   │        release.status = ACTIVE
   │      - 任一 FAILED → 广播 PLUGIN_ROLLBACK，已加载实例卸载新版本
   │        release.status = ROLLBACK，发布失败，人工介入
   │
   ▼ 5. 激活后，注册中心持续健康检查（见 12.7）
```

**两阶段的意义**：阶段1只"装载"不"激活"，阶段2统一"切换"。这样在装载期间业务仍由旧版本服务，不会出现半加载对外可见的行为分裂。这是 C1、C3 的核心解法。

### 12.5 一致性保证策略

#### 12.5.1 版本屏障

- 注册中心以 `(pluginId, releaseId)` 为版本屏障单位。
- 实例心跳上报 `loadedPlugins`（含版本），注册中心比对：若某实例版本 ≠ 当前 ACTIVE 版本，标记该实例 `INCONSISTENT`。
- 不一致实例的处理：**摘流**（从注册中心/网关路由摘除）或**触发重载**（可配置策略），避免脏请求。

#### 12.5.2 强一致加载（失败回滚）

如 12.4 步骤4，任一实例装载失败即整体回滚，保证不出现"部分实例新版本已激活"的中间态。

#### 12.5.3 灰度发布

- `releaseStrategy=CANARY`：先只对 `canaryInstances` 装载+激活，其余实例保持旧版本。
- 网关/注册中心按路由规则把指定流量（如按租户、用户灰度标）路由到灰度实例。
- 灰度验证通过后，发起全量发布（对剩余实例走 12.4 流程）。
- 灰度期间存在"双版本并存"，但通过路由隔离保证同一请求只落到一种版本，不破坏单请求一致性。

#### 12.5.4 网络分区容忍

- 分区内的实例无法回报 → 注册中心视为 `STALE`，按策略摘流（分区实例不接新流量），避免分区实例用旧插件服务。
- 分区恢复后，实例心跳恢复，注册中心比对版本，触发对齐重载。

### 12.6 插件与服务的亲和性（解决 C4 的关键）

**原则：插件应与它所扩展的业务部署在同一微服务内。**

- 插件在 `plugin.yml` 声明 `targetServices`，注册中心据此分发。
- 设计约束：`ActionHook`/`StateChangeListener` 这类**事务内同步钩子**只能作用于本服务内的业务（本地事务）。若某业务的状态变化需要触发另一服务的同步逻辑，那不是"插件钩子"，而应走异步事件（MQ）。
- 这样 90% 的 R5 场景（保存时的前置/后置钩子、状态变更的同步监听）都在本地事务内解决，无需分布式事务。

### 12.7 跨服务事务一致性（C4 的分层解法）

按场景分层，避免一刀切上 Seata：

| 场景 | 方案 | 一致性 | 说明 |
|------|------|--------|------|
| 插件钩子 + 事件监听在同一服务 | 本地编程式事务（原方案第5章） | 强一致 | 主路径，覆盖 90% |
| 状态变化后通知下游服务 | RocketMQ 事务消息 | 最终一致 | DB 提交→半消息commit→下游消费幂等 |
| 跨服务同步调用且需强一致 | Seata AT 模式（插件可选依赖） | 强一致 | 少数场景，插件自带 Seata SDK，平台不强制 |
| 跨服务批量/长链路 | Saga 模式（补偿） | 最终一致 | 由编排引擎或插件实现补偿 |

**Seata 作为插件可选依赖**：平台核心不引入 Seata；需要跨服务强一致的插件在 `plugin.yml` 声明 `dependencies: seata-spring-boot-starter`，由该插件的 ClassLoader 加载。这样不污染平台核心，也满足"不修改原平台"。

**决策原则**：默认走"本地事务 + MQ 事务消息"；只有当业务上无法接受最终一致（如跨服务扣款+扣库存必须同时成功失败）才用 Seata，且要评审。

### 12.8 元数据跨服务一致（C5）

```
元数据存储：共享库（或 Nacos/配置中心）作为唯一真相源
   │
   ▼ 各服务启动时全量拉取 → 本地 ConcurrentHashMap（一级缓存）
   │
   ▼ Redis 存元数据版本号 + 热点元数据副本（二级缓存）
   │
   ▼ 元数据变更：写共享库 → 发 META_CHANGED(v+1) MQ 广播
   │
   ▼ 各服务收到广播 → 比对本地版本号 → 拉取增量 → 刷新本地缓存
```

- 本地缓存查询零网络开销；版本号比对用 Redis（轻量）。
- 变更窗口内各服务可能有秒级不一致，对"元数据"可接受（元数据变更低频）；若不可接受，元数据读取可加版本号校验回源。
- 元数据变更本身也走"两阶段"：先写库+发广播，各服务刷新成功才视为变更生效（可选，元数据低频可简化）。

### 12.9 集群协调与故障自愈（C6）

| 故障 | 检测 | 处理 |
|------|------|------|
| 实例装载失败 | 回报 FAILED | 发布回滚；单实例失败可配置"跳过+告警"或"阻断" |
| 实例宕机 | 心跳超时 | 标记 OFFLINE，摘流；恢复后心跳恢复，比对版本触发对齐 |
| 网络分区 | 心跳中断 | 分区实例摘流；分区恢复后重载对齐 |
| 版本漂移 | 心跳版本 ≠ ACTIVE | 摘流或自动重载（按策略） |
| ClassLoader 泄漏 | 监控指标（老版本引用计数） | 告警 + 定期重启兜底 |
| 注册中心单点 | — | 注册中心自身高可用（主从/集群） |

### 12.10 对原开发计划的修订

| 阶段 | 新增任务 |
|------|----------|
| P2 | T2.8 `PluginAgent`（心跳、指令接收、拉取、回报）<br>T2.9 插件注册中心（元信息、发布编排、结果聚合）<br>T2.10 两阶段生效（装载→激活）<br>T2.11 版本屏障与健康检查 |
| P3 | T3.5 跨服务事件：RocketMQ 广播 PLUGIN_LOAD/UNLOAD/META_CHANGED<br>T3.6 Seata AT 可选依赖打包方案（插件侧） |
| P5 | T5.5 注册中心鉴权与签名<br>T5.6 不一致实例摘流策略<br>T5.7 插件一致性监控指标（版本分布、装载耗时、不一致实例数） |

里程碑补充：
- **M2'**：插件在多实例间两阶段一致发布跑通
- **M3'**：跨服务状态事件经 MQ 事务消息端到端最终一致

### 12.11 微服务一致性风险评估

| 风险 | 等级 | 应对 |
|------|------|------|
| 两阶段激活期间旧版本卸载内存泄漏 | 中 | 引用计数 + 延迟卸载 + 监控 |
| 注册中心单点故障 | 高 | 注册中心高可用部署 |
| 心跳风暴（实例多） | 低 | 心跳聚合 + 合并上报 |
| 灰度路由与插件版本错配 | 中 | 路由规则与插件版本绑定校验 |
| Seata 引入复杂度 | 中 | 严格评审，仅强一致场景用 |
| 元数据变更秒级不一致 | 低 | 版本号校验，必要时回源 |
| 分区实例用旧插件服务 | 高 | 分区摘流（不接新流量） |

### 12.12 小结

- **C1/C2/C3（分发与版本一致）**：插件注册中心 + 两阶段生效 + 版本屏障 + 健康检查，可行。
- **C4（跨服务事务）**：亲和性原则 + 分层方案（本地事务 / MQ事务消息 / Seata可选），覆盖且不过度设计。
- **C5（元数据一致）**：共享真相源 + 本地缓存 + 版本号广播，可行。
- **C6（故障自愈）**：心跳 + 摘流 + 重载对齐，可行。

**结论：微服务架构下插件一致性可保证，方案落地。核心是"插件注册中心 + 两阶段生效 + 亲和性部署 + 分层事务"。**

## 13. 字段变更事件与组合条件捕捉（补充设计）

> 用户澄清：状态变更可能只是任意一个表单字段，需支持**任意字段变更捕捉**与**多字段组合条件**捕捉。原方案第 4 章仅围绕状态机字段（statusField）做事件，本章将其扩展为通用的字段变更事件框架。

### 13.1 需求澄清与两种场景区分

| 类型 | 触发时机 | 执行位置 | 配置存储 | 前端运行时要改吗 |
|------|----------|----------|----------|------------------|
| **A. 后端数据变更事件**（R4 本意） | 数据保存到 DB 时（update） | 后端（事务内插件 + 事务后 MQ） | 后端配置表 + schema | **不用**，只改设计器配置入口 |
| **B. 前端表单联动** | 用户填表时字段值变 | 前端运行时 | schema 内 | **要改 RendererNode** |

本章以 **A** 为主线（用户核心诉求：数据变更捕捉 + 自定义业务代码 + 事务一致），**B** 作为可选补充（13.6）。

### 13.2 后端方案

#### 13.2.1 配置模型

新增"字段变更事件规则"配置表：

```sql
lc_field_change_event (
  id, bizCode, pageId,              -- 归属业务/页面
  eventCode, eventName,
  triggerType,                      -- ANY_CHANGE / ALL_CHANGE / EXPRESSION
  watchFields,                      -- 监听字段列表（JSON: ["amount","currency"]），来自表单 fieldName
  conditionExpr,                    -- 组合条件表达式（SpEL，可用 changed()/old()/new() 函数）
  firePhase,                        -- SYNC（事务内，调插件）/ ASYNC（事务后，投MQ）/ BOTH
  syncPluginId,                     -- 同步处理插件ID（实现 FieldChangeListener）
  asyncTopic,                       -- 异步处理 MQ topic
  enabled, sortNo, remark
)
```

- `triggerType=ANY_CHANGE`：`watchFields` 中任一字段变更即触发
- `triggerType=ALL_CHANGE`：`watchFields` 中全部字段都变更才触发
- `triggerType=EXPRESSION`：用 `conditionExpr` 自定义组合条件（最灵活，覆盖前两者）

#### 13.2.2 组合条件表达式引擎

后端在 update 执行时，先查出 oldValues（update 前快照），执行 update，再计算变更字段集合，用 SpEL 求值条件。表达式上下文提供三个内置函数：

| 函数 | 含义 | 示例 |
|------|------|------|
| `changed('f')` | 字段 f 是否变更 | `changed('amount')` |
| `old('f')` | 字段 f 的旧值 | `old.status == 'DRAFT'` |
| `new('f')` | 字段 f 的新值 | `new.amount > 10000` |

组合条件示例：
- 任一变更：`changed('amount') || changed('currency')`
- 全部变更：`changed('amount') && changed('currency')`
- 组合带值：`changed('amount') && new.amount > 10000 && old.status == 'DRAFT'`
- 跨字段关联：`changed('unitPrice') && changed('qty') && new.amount != new.unitPrice * new.qty`（校验类捕捉）

SpEL 求值由 `ConditionEvaluator` 完成，`changed/old/new` 作为 SpEL 自定义函数注册。表达式白名单校验（禁止反射调用 `T(...)`、`new` 等），防注入。

#### 13.2.3 执行流程（嵌入原事务编排）

在 `CrudExecutor.execute` 处理 `action=update` 时：

```
1. oldValues = queryById(bizCode, id)              // update 前快照（复用乐观锁查询）
2. 执行 update SQL
3. changedFields = { f | old[f] != new[f] }        // 计算变更字段集合
4. rules = FieldChangeEventRegistry.get(bizCode)   // 取该业务的事件规则
5. matched = rules.filter(r -> ConditionEvaluator.eval(r, oldValues, newValues, changedFields))
6. for r in matched:
     if r.firePhase in (SYNC, BOTH):
         PluginContainer.invokeFieldChangeListener(r.syncPluginId, event)   // 事务内，抛异常回滚
     if r.firePhase in (ASYNC, BOTH):
         EventBus.fireAsync(r.asyncTopic, event)                            // 事务后 MQ
```

- 步骤 1~6 全部在原 `TransactionOrchestrator` 编程式事务内（第 5 章），满足 R5 事务一致性。
- `FieldChangeListener` 是新增 SPI（见 13.2.4），与 `StateChangeListener` 平级，事务内同步执行。
- create 操作：可配置"create 视为所有字段新增"（`changed('f') = true, old('f') = null`），也可单独配 `onCreate` 规则。
- delete 操作：可配置"delete 视为所有字段移除"，触发清理类事件。

#### 13.2.4 新增 SPI

```java
// 字段变更监听（事务内同步，可参与事务）
public interface FieldChangeListener extends Plugin {
    boolean support(String bizCode, String eventCode);
    void onFieldChange(FieldChangeEvent evt);   // evt 含 oldValues/newValues/changedFields/eventCode
    // 抛异常将回滚整事务
}
```

`FieldChangeEvent`：`{ bizCode, eventCode, businessId, oldValues, newValues, changedFields, firedBy }`。

#### 13.2.5 与状态机事件的关系

状态机事件（第 2.3 节）降级为字段变更事件的**特例**：
- 状态机迁移 = `statusField` 字段变更 + 迁移合法性校验 + 产出 `StateChangeEvent`。
- 可统一到字段变更事件框架：状态机规则作为内置的 `triggerType=EXPRESSION` 规则，`conditionExpr = changed('{statusField}') && inStateMachineTransition(...)`。
- 这样事件总线只有一套，状态机事件、字段变更事件、自定义事件统一调度，避免多套机制并存。

#### 13.2.6 性能与边界

- oldValues 查询：update 多数场景本就要先查（乐观锁、权限、状态校验），**复用同一查询**，无额外开销。
- changedFields 计算：字段数有限，O(n) 比较，开销可忽略。
- 规则匹配：规则数有限（单业务通常 < 20），线性扫描 + SpEL 求值，开销小；可按 `watchFields` 建倒排索引加速（规则多时）。
- **边界**：批量 update 时，逐条对比可能开销大；批量场景建议只支持 `EXPRESSION` 且表达式仅依赖聚合值，或走异步批量事件（事务后扫表对比）。

## 15. 对外 API 与字段映射（补充设计）

> 用户需求：① 每个页面功能标准化后，API 应能直接对外提供；② 对外时引用字段（如物料大类）内部用数据库主键，外部用业务编码，需处理映射。

### 15.1 问题1 回答：能否直接对外？

**方向正确，但内部网关不能直接暴露。** 原因：

| 问题 | 说明 |
|------|------|
| 字段语义错位 | 内部用主键/内部字段名，外部应用业务编码/对外字段名（问题2） |
| 安全 | 内部网关无对外鉴权/限流，schema 暴露内部结构 |
| 契约稳定 | 内部 schema 变更会破坏外部调用方，需版本化隔离 |
| 文档 | 对外需 OpenAPI 文档，内部网关无 |

**方案：对外 API 适配层（ExternalApiAdapter）**，作为内部网关之外的第二个入口，底层复用通用引擎（CrudExecutor/TransactionOrchestrator/StateMachine/事件/插件），不重造轮子。

```
外部调用方
  ↓ POST /api/external/{apiCode}/{action}
对外 API 网关（鉴权 Token/签名 · 限流 · 版本 · 幂等）
  ↓
ExternalApiAdapter（字段映射适配层）
  · 入站：externalField→internalField，编码→主键
  · 调用通用引擎（复用，同事务）
  · 出站：internalField→externalField，主键→编码
  ↓
通用后台引擎（第 2/5 章原样复用）
```

### 15.2 问题2 回答：主键 ↔ 业务编码映射

核心是给每个对外 API 配一份**字段映射表**，声明每个字段的对外名、暴露范围、值转换方式。

#### 15.2.1 配置模型

```sql
lc_external_api (
  id, apiCode,              -- 对外API编码（如 material）
  bizCode,                  -- 对应内部业务编码（如 material）
  apiName, version,         -- API 版本（v1/v2）
  authType,                 -- TOKEN / SIGNATURE
  idempotent,               -- 是否幂等（写入用业务编码做幂等键）
  enabled
)

lc_external_field_mapping (
  id, apiCode,
  internalField,            -- 内部字段名（如 materialCategoryId）
  externalField,            -- 对外字段名（如 materialCategoryCode）
  expose,                   -- READ / WRITE / BOTH / NONE
  mappingType,              -- DIRECT / REF_CODE / EXPRESSION / CUSTOM_PLUGIN
  refBizCode,               -- 引用业务编码（REF_CODE 时，如 materialCategory）
  refCodeField,             -- 引用表业务编码字段（如 categoryCode）
  refIdField,               -- 引用表主键字段（如 id）
  expr,                     -- EXPRESSION 时的 SpEL
  pluginId,                 -- CUSTOM_PLUGIN 时的插件
  sortNo
)
```

#### 15.2.2 映射类型

| 类型 | 用途 | 转换逻辑 |
|------|------|----------|
| `DIRECT` | 字段名转换，值不变 | materialName → materialName |
| `REF_CODE` | **外键主键 ↔ 业务编码**（问题2 核心） | 入站：编码→查引用表得主键；出站：主键→查引用表得编码 |
| `EXPRESSION` | SpEL 表达式转换 | 单位换算、拼接等 |
| `CUSTOM_PLUGIN` | 复杂映射走插件 | 跨表聚合、外部系统补全等 |

#### 15.2.3 REF_CODE 转换流程（物料大类示例）

配置：`internalField=materialCategoryId, externalField=materialCategoryCode, refBizCode=materialCategory, refCodeField=categoryCode, refIdField=id`

**入站（外部创建/更新物料）**：
```
external { materialCategoryCode: "A01" }
  → 适配层查 materialCategory 表 where categoryCode='A01' → id=123
  → 若编码不存在：返回明确业务错误码 EX_REF_CODE_NOT_FOUND，不静默置空
  → 交给引擎 { materialCategoryId: 123 }
```

**出站（外部查询物料）**：
```
引擎返回 { materialCategoryId: 123, ... }
  → 适配层查 materialCategory 表 where id=123 → categoryCode='A01'
  → 返回外部 { materialCategoryCode: "A01", ... }
```

#### 15.2.4 性能优化

- **缓存**：引用表（物料大类等基础数据）量小且稳定，编码↔主键映射**复用现有基础数据缓存**，命中率高。
- **批量转换**：列表查询返回 N 条，批量收集引用 id 集合 → 一次查引用表 → 回填，避免 N+1。
- **缓存失效**：引用表数据变更时（字段变更事件）失效对应缓存键。

#### 15.2.5 主键与定位

- 内部主键 `id` 默认 `expose=NONE`，不对外暴露。
- 外部更新/删除/查询用**业务编码**定位记录（如 `materialCode`），而非 id。
- 前提：业务表需有唯一业务编码字段（基础资料通常有编码，单据有单号）。无业务编码的表不适合直接对外，需走插件定制。

### 15.3 查询条件的映射

对外查询的过滤条件也用外部字段名 + 编码，适配层同样转换：
```
外部 GET /api/external/material?materialCategoryCode=A01&status=ACTIVE
  → 转换为内部 { materialCategoryId: 123, status: 'ACTIVE' }
  → 引擎按内部字段查询
```
排序字段、分页参数同理转换字段名。

### 15.4 与现有方案的整合

| 复用 | 说明 |
|------|------|
| 通用引擎 | CrudExecutor/StateMachine/事件/事务编排原样复用，适配层只是另一个入口 |
| 插件机制 | 复杂映射走 `FieldMapperPlugin` SPI（新增），入站/出站各一个钩子 |
| 字段变更事件 | 引用表变更时触发缓存失效（第 13 章事件订阅） |
| 元数据配置 | 字段映射配置可由配置页面/设计器维护，随 schema 持久化 |
| 权限体系 | 对外 API 鉴权独立于内部权限（G3），用 Token/签名 |

### 15.5 新增 SPI

```java
// 字段映射插件（复杂转换）
public interface FieldMapperPlugin extends Plugin {
    boolean support(String apiCode, String field, Direction dir);   // dir=INBOUND/OUTBOUND
    Object map(Object value, MappingContext ctx);
}
```

### 15.6 对外 API 的完整能力清单

| 能力 | 说明 |
|------|------|
| 鉴权 | Token / HMAC 签名，独立于内部用户体系 |
| 限流 | 按 apiCode + 调用方限流（Sentinel/Redis） |
| 版本 | apiCode + version，字段映射可按版本配 |
| 幂等 | 写入用外部业务编码做幂等键，防重复提交 |
| 字段映射 | 本章核心，DIRECT/REF_CODE/EXPRESSION/PLUGIN |
| 错误码 | 对外用业务错误码（如 EX_REF_CODE_NOT_FOUND），不泄露内部栈 |
| 文档 | 根据 mapping 配置自动生成 OpenAPI 3 文档 |
| 审计 | 对外调用日志（谁/何时/哪个API/入参摘要/结果） |

### 15.7 开发计划补充

| 阶段 | 新增任务 | 里程碑 |
|------|----------|--------|
| P1（引擎） | T1.11 `lc_external_api`/`lc_external_field_mapping` 表 + `ExternalApiAdapter` 骨架 | — |
| P1 | T1.12 `REF_CODE` 转换器（缓存 + 批量） + `DIRECT`/`EXPRESSION` | M1''：对外 API 物料查询/创建端到端 |
| P2（插件） | T2.13 `FieldMapperPlugin` SPI | — |
| P5（安全） | T5.8 对外鉴权（Token/签名）+ 限流 + 幂等 | — |
| P6（配置） | T6.6 对外 API 与字段映射配置页面 + OpenAPI 文档生成 | M6''：自助配置对外 API |

### 15.8 风险补充

| 风险 | 等级 | 应对 |
|------|------|------|
| 引用编码不存在导致脏数据 | 高 | 入站校验，不存在即报错回滚，不静默置空 |
| 缓存与引用表不一致 | 中 | 引用表变更事件触发失效；查询可加版本号校验 |
| 批量转换 N+1 | 中 | 批量收集 id 一次查询回填 |
| 对外契约被内部 schema 变更破坏 | 中 | 字段映射层隔离 + API 版本化 |
| 无业务编码的表无法对外 | 低 | 走插件定制或先补业务编码字段 |
| 对外暴露敏感字段 | 高 | expose 默认 NONE，显式开放；安全评审 |

### 15.9 小结

- **问题1**：不能直接暴露内部网关，需对外 API 适配层（鉴权/限流/映射/契约），底层复用通用引擎。
- **问题2**：用字段映射配置解决，`REF_CODE` 类型处理外键主键↔业务编码转换，入站编码→主键、出站主键→编码，缓存+批量优化，不存在即报错。主键默认不对外，外部用业务编码定位。
- **整合**：复用引擎/插件/事件/元数据，新增适配层 + 映射配置 + `FieldMapperPlugin` SPI，不改动核心。

## 16. 审批流设计（补充设计，对应缺口 G4）

> 之前第 14 章将审批流列为缺口 G4（P1）未详细设计。本章补全：选型、流程模型、与现有机制整合、前端需增加的功能。

### 16.1 选型：自研轻量审批引擎（推荐）

| 方案 | 适合场景 | 取舍 |
|------|----------|------|
| **自研轻量**（推荐） | 单据审批：串行/会签/或签/条件分支/驳回/加签/转办 | 与"配置驱动"契合，流程定义即配置；复用状态机/字段变更事件/插件/事务编排；表少、轻、可控 |
| Flowable/Activiti | 复杂 BPMN（子流程/事件网关/补偿事件） | 重、20+张表、学习陡、与配置驱动有张力；若未来真需要，可作为插件引入，不污染平台 |

低代码单据审批 90% 是"多节点 + 会签/或签 + 条件分支 + 驳回"，自研轻量完全覆盖。**决策点：是否需要子流程/事件网关等 BPMN 高级能力？若无，选自研。**

### 16.2 流程定义模型（配置驱动）

```sql
lc_workflow_def (
  id, workflowCode, workflowName, bizCode,     -- 绑定业务
  version, status,                             -- DRAFT/ACTIVE
  triggerAction,                               -- 触发动作（submit 下达时启动）
  startState, endState, rejectState,           -- 流程结束/驳回后业务状态
  remark
)

lc_workflow_node (
  id, workflowCode, version, nodeCode, nodeName,
  nodeType,                                    -- START/APPROVAL/CONDITION/END
  approverType,                                -- USER/ROLE/DEPT/LEADER/EXPR/PLUGIN
  approverExpr,                                -- 审批人解析（ID列表/角色/表达式/插件ID）
  approveMode,                                 -- SEQUENCE(依次)/PARALLEL(会签)/ANY(或签)
  passCondition,                               -- 通过条件（ALL/ANY/RATIO）
  rejectTo,                                    -- 驳回到（PREV/START/指定节点）
  allowAddApprover, allowTransfer,             -- 允许加签/转办
  timeoutMinutes, timeoutAction,               -- 超时分钟 + 动作（AUTO_PASS/REMIND/ESCALATE）
  prePlugin, postPlugin,                       -- 节点前置/后置插件（事务内）
  sortNo
)

lc_workflow_transition (                       -- 节点流转（含条件分支）
  id, workflowCode, version, fromNode, toNode,
  conditionExpr,                               -- 分支条件（SpEL，基于业务数据）
  sortNo
)
```

### 16.3 流程实例与任务

```sql
lc_workflow_instance (
  id, workflowCode, version, bizCode, businessId,  -- 业务记录
  currentNode, status,                             -- RUNNING/APPROVED/REJECTED/CANCELED
  startUser, startTime, endTime
)

lc_workflow_task (
  id, instanceId, nodeCode, assignee,             -- 审批人
  taskStatus,                                      -- PENDING/APPROVED/REJECTED/TRANSFERRED/ADDED
  comment,                                         -- 审批意见
  operateTime, operator
)
```

### 16.4 与现有机制的整合（核心：不新造轮子）

| 整合点 | 复用 | 说明 |
|--------|------|------|
| 下达触发 | StateMachine（2.3） | `submit` → 查 bizCode 是否绑 workflow → 启动实例 + 首个任务 |
| 审批通过回写状态 | 字段变更事件（13章） | 到 END → 回写 endState → 状态变更自动触发订阅者/插件/MQ |
| 节点插件 | TransactionOrchestrator（5章） | 节点 pre/post 插件在同一事务内，满足 R5 |
| 审批人解析 | 插件 SPI | USER/ROLE/DEPT/上级 内置，复杂走 `ApproverResolverPlugin` |
| 催办/超时通知 | 消息通知（I1） | 定时任务扫超时 → 发通知 |
| 撤销 | StateMachine | 业务 revoke → 取消流程实例 |
| 审批轨迹 | 数据审计（D1） | 任务操作天然是审计流水 |

### 16.5 审批操作

同意 / 驳回（驳回到 rejectTo）/ 转办（换审批人）/ 加签（增审批人）/ 撤回（发起人撤回未审任务）。每个操作在事务内：更新任务状态 → 判断节点是否通过 → 流转 → 必要时回写业务状态 + 触发事件。

## 17. 元数据驱动深度对比与可借鉴设计（苍穹 vs 本方案）

> 用户要求详细解释第 6.9.3 节四个对比项。逐个展开：苍穹怎么做、本方案怎么做、区别、可借鉴落地设计。

### 17.1 元数据分层继承

**苍穹**：三层元数据——产品层（金蝶标准产品出厂）→ 行业层 → 客户层。运行时从下到上**合并**：上层自动继承下层所有字段/操作/布局，可**新增**（加字段）、可**覆盖**（改字段属性如必填、校验规则）。客户层只记录"我加了什么/改了什么"，**不碰产品层原始定义**。

举例：金蝶标准采购订单 = [单号,供应商,日期,金额]。客户A 在客户层加 [项目编码,成本中心] → 运行时合并成 [单号,供应商,日期,金额,项目编码,成本中心]。金蝶升级标准产品加了 [币种] → 客户A 的采购订单自动变 [单号,供应商,日期,金额,币种,项目编码,成本中心]，**客户A 没改产品层，自动兼容升级**。

**本方案**：单层 `lc_biz_meta`，一份元数据。加字段只能改这份（侵入平台），或靠插件（但插件改**行为**不改**结构**）。平台若提供"标准采购订单"，客户想加字段无机制——只能改原定义，升级就冲突。

**区别**：苍穹结构层扩展有分层不侵入；本方案结构层扩展无机制。

**可借鉴落地**：
```sql
lc_biz_meta 增加：
  layer,            -- PLATFORM / INDUSTRY / CUSTOMER
  parentBizCode,    -- 继承的父业务编码
  overrideFields    -- 本层覆盖/新增的字段（增量，非全量）
```
运行时 `MetaRegistry.getMerged(bizCode)`：先加载 PLATFORM 层，再 INDUSTRY 覆盖/扩展，再 CUSTOMER 覆盖/扩展，返回合并后的完整元数据。客户层只存增量。**与插件互补：分层改结构（加字段/改属性），插件改行为（保存逻辑/事件处理）**。平台升级 = PLATFORM 层出新版，CUSTOMER 层自动兼容。

### 17.2 元数据范围

**苍穹**：**一切皆元数据**——业务对象、字段、操作、表单布局、列表布局、报表、审批流程、权限、数据规则、校验规则、编号规则，全部是元数据，统一存元数据库，运行时统一由元数据引擎驱动。好处：统一管理/版本/导入导出/升级/分层。

**本方案**：元数据只覆盖部分（页面 schema + lc_biz_meta/field/action/state_machine + 第 16 章流程）。权限只有 `permissionExpr` 表达式无完整元数据；报表未设计；校验只有 `validationExpr`；列表布局散在页面 schema 里。**散落各表，没有统一元数据体系**。

**区别**：苍穹所有配置都是元数据统一驱动；本方案只覆盖部分，其余散落。

**可借鉴落地**：把权限、报表、列表布局、校验规则、编号规则也纳入元数据，建立统一 `MetaRegistry` 管理所有类型（按 metaType 分类）。好处：统一版本/导入导出/升级/分层。**不必像苍穹那么重，按需纳入**——优先把权限（G3）和校验纳入，报表/列表后续按需。

### 17.3 元数据版本化

**苍穹**：元数据带版本号，变更存历史可回滚。产品升级 = PLATFORM 层出新版本，客户层通过继承自动兼容。苍穹有元数据升级工具自动处理字段重命名/类型变更的兼容性。

**本方案**：无版本化。改了就是改了，无历史、不能回滚（第 14 章 F1 提了但未设计）。平台升级改标准元数据时，客户的修改直接冲突（因为单层，客户修改改在唯一一份上）。

**区别**：苍穹有版本/可回滚/升级自动兼容；本方案无版本/升级冲突。

**可借鉴落地**：`lc_biz_meta` 加 `version`，每次变更存历史版本（`lc_biz_meta_history`）。配合分层：平台升级 = PLATFORM 出新版，CUSTOMER 自动兼容。元数据变更走版本化发布（类似插件两阶段生效，先发布再激活）。可回滚到历史版本。

### 17.4 应用包

**苍穹**：**应用包/开发方案**——把一个业务领域的所有产物打包：元数据 + 插件(jar) + 页面 + 权限 + 流程 + 配置。整体部署/迁移/升级。如把"采购管理"从开发迁到生产，所有相关产物一起走，不遗漏。应用包有版本，整体升级。

**本方案**：插件 jar 单传、元数据单配、页面 schema 单存、权限流程各自配。**没有整体打包概念**。迁移一个业务要分别迁元数据/插件/页面/权限/流程，容易遗漏。

**区别**：苍穹一个业务整体打包迁移；本方案零散管理易遗漏。

**可借鉴落地**：设计"应用包"——一个业务（如采购管理）的元数据+插件+页面+权限+流程打成一个 zip：
```
purchase-management-v1.0.zip
  ├── metadata.json        # 业务元数据（lc_biz_meta 等）
  ├── plugins/*.jar        # 相关插件
  ├── schemas/*.json       # 页面 schema
  ├── permissions.json     # 权限配置
  └── workflows.json       # 流程定义
```
整体部署到目标环境，带版本整体升级，部署时校验依赖与兼容性。迁移一个业务 = 传一个 zip，不遗漏。

### 17.5 四项优先级与建议

| 项 | 价值 | 难度 | 建议 |
|----|------|------|------|
| 分层继承 | 高（解决结构层扩展不改平台） | 中 | **优先做**，与插件互补 |
| 元数据范围统一 | 中 | 中 | 按需纳入，优先权限/校验 |
| 版本化 | 中 | 低 | 配合分层一起做 |
| 应用包 | 中 | 中 | 业务多了再做 |

**核心**：最值得学的是**分层继承**——它补上了本方案"结构层扩展不改平台"的缺口，与插件（行为层扩展）互补，且是苍穹这类成熟 PaaS 的核心机制。其余三项按需推进。

## 18. 元数据优化文档目的

### 四个方向

| 方向 | 苍穹核心 | 本文档优化重点 |
|------|---------|---------------|
| 1. 元数据分层继承 | 产品/行业/客户三层合并 | 属性级覆盖、合并缓存、合并溯源、显式删除、冲突检测 |
| 2. 一切皆元数据统一驱动 | 一切皆元数据 | 分域子引擎、元数据依赖图、生命周期治理、命名空间 |

1. **优化而非照搬**：每个方向先分析苍穹不足，再给改进点
2. **可落地**：给数据模型、运行时机制、落地步骤

4. **渐进式**：可分阶段落地，不必一步到位

## 19. 方向一：元数据分层继承

### 19.1 苍穹做法

产品层（金蝶标准产品出厂）→ 行业层 → 客户层，运行时从下到上合并：上层继承下层所有字段/操作/布局，可新增（加字段）、可覆盖（改字段属性）。客户层只记录增量，不碰产品层。产品升级时客户层自动兼容。

### 19.2 苍穹不足（可优化点）

| 不足 | 问题 |
|------|------|
| **覆盖粒度粗** | 覆盖是整字段级，只想改字段一个属性（如只改 label 不改 type）也要整字段覆盖，容易把其他属性意外回退到下层值 |
| **合并性能** | 每次运行时合并三层，层数多/元数据大时有开销 |
| **合并黑盒** | 合并后看不出"这个字段哪层加的、哪个属性哪层改的"，调试难 |
| **删除语义模糊** | 上层想"删除"下层字段（而非覆盖），语义不清 |
| **冲突靠人工** | 字段重命名/类型变更等冲突靠升级工具人工处理，易错 |

### 19.3 我们的优化

#### 优化1：属性级覆盖（而非字段级）

覆盖记录到**属性粒度**——只记录本层改了哪个属性，不整字段覆盖。

```
产品层字段 amount: { type:decimal, label:"金额", required:true, scale:2 }
客户层只改 label → overrideProps: { label:"采购金额" }
合并结果: { type:decimal, label:"采购金额", required:true, scale:2 }
                                          ↑ 保留产品层，不意外回退
```

#### 优化2：声明式合并策略

每个属性声明合并策略，而非硬编码合并逻辑：

| 策略 | 含义 | 适用 |
|------|------|------|
| OVERRIDE | 上层值覆盖下层 | 字段属性（label/type/required） |
| MERGE | 上下层合并（去重） | 校验规则、事件订阅 |
| APPEND | 上层追加到下层列表 | 列表字段、操作按钮 |
| REJECT | 上层不允许改该属性 | 主键、字段名（防破坏） |

#### 优化3：合并结果缓存

合并后的元数据缓存（key = bizCode + 各层 version），不每次重新合并。任一层版本变更 → 失效重算。

#### 优化4：合并溯源

合并结果记录每个字段/属性来自哪一层（`sourceLayer`），支持可视化 diff："这个 label 是客户层改的，type 是产品层定义的"。便于调试和审计。

#### 优化5：显式删除

上层"删除"下层字段用显式 `removedFields` 声明，语义清晰，区别于"覆盖成空"。删除时校验：是否有业务数据/流程/权限依赖该字段，有则警告。

#### 优化6：冲突检测

保存时检测破坏性变更（改字段 type、缩 length、删字段），标记 `BREAKING`，要求显式迁移脚本（对接方向3），不静默通过。

### 19.4 数据模型

```sql
-- 元数据层定义
lc_meta_layer (
  id, layerType,          -- PLATFORM / INDUSTRY / CUSTOMER
  layerCode, layerName, parentLayer, priority   -- priority 决定合并顺序
)

-- 业务元数据增加分层字段
lc_biz_meta 增加:
  layerType, parentBizCode, baseVersion   -- baseVersion: 继承的父层版本

-- 字段元数据改为增量记录
lc_field_meta 增加:
  layerType, bizCode, fieldName,
  isNew,                  -- 本层新增的字段
  overrideProps,          -- 本层覆盖的属性（JSON，属性级，只记录改的）
  isRemoved,              -- 本层显式删除下层字段
  sourceLayer             -- 溯源：该字段最终来自哪层（合并后填）

-- 属性合并策略
lc_merge_rule (
  metaType, propName, strategy   -- OVERRIDE/MERGE/APPEND/REJECT
)
```

### 19.5 运行时合并机制

```
MetaRegistry.getMerged(bizCode):
  1. 取各层元数据（按 priority: PLATFORM → INDUSTRY → CUSTOMER）
  2. 检查缓存（key = bizCode + 各层 version），命中则返回
  3. 从 PLATFORM 开始逐层合并：
     for each layer in priority order:
       for each field in layer.fields:
         if field.isNew:        加入结果
         if field.isRemoved:    从结果移除（先校验依赖）
         if field.overrideProps: 按 lc_merge_rule 逐属性合并
           OVERRIDE: 结果[prop] = layer[prop]
           MERGE:     结果[prop] = merge(结果[prop], layer[prop])
           APPEND:    结果[prop] = 结果[prop] + layer[prop]
           REJECT:    忽略（不允许改）
         记录 sourceLayer（溯源）
  4. 缓存合并结果
  5. 返回合并元数据 + 溯源信息
```

### 19.6 落地步骤

1. `lc_biz_meta`/`lc_field_meta` 加 `layerType`/`parentBizCode`/`overrideProps` 等字段
2. 实现 `MetaMerger`（按 `lc_merge_rule` 合并）+ 缓存 + 溯源
3. 现有单层元数据迁移为 PLATFORM 层
4. 元数据配置页面支持选层编辑（客户层只显示增量编辑）— **前端详见前端设计文档**
5. 合并 diff 可视化（哪个属性哪层改的）— **前端详见前端设计文档**
6. 冲突检测 + BREAKING 标记

## 20. 方向二：一切皆元数据统一驱动

### 20.1 苍穹做法

一切皆元数据（业务对象/字段/操作/表单/列表/报表/流程/权限/校验/编号），统一存元数据库，运行时统一由元数据引擎驱动。

### 20.2 苍穹不足

| 不足 | 问题 |
|------|------|
| **引擎臃肿** | 一个引擎驱动所有元数据类型，越来越重，难维护 |
| **元数据耦合** | 类型间依赖复杂（流程引用字段、权限引用字段），变更影响难追踪 |
| **缺乏治理** | 元数据多了之后谁定义的、给谁用、是否冗余，无治理 |
| **类型膨胀** | 所有配置都是元数据，类型越来越多 |

### 20.3 我们的优化

#### 优化1：分域分类 + 独立子引擎（避免臃肿）

元数据按**域**分类，每域有独立子引擎，统一注册但独立驱动。避免苍穹一个臃肿引擎。

| 域 | 包含元数据 | 子引擎 |
|----|-----------|--------|
| **结构域** STRUCTURE | 业务对象/字段/关系 | CrudExecutor |
| **行为域** BEHAVIOR | 操作/状态机/事件/校验/编号 | ActionExecutor / StateMachine / EventBus / Validator |
| **展现域** PRESENTATION | 表单布局/列表布局/报表/打印 | RenderEngine |
| **控制域** CONTROL | 权限/流程/数据规则 | AuthEngine / WorkflowEngine |

统一 `MetaRegistry` 按 `metaType` 路由到对应子引擎，各子引擎独立演进。

#### 优化2：元数据依赖图（变更影响分析）

维护元数据间依赖关系，变更时做影响分析（第 14 章 F4）：

```
改字段 amount → 影响分析：
  - 表单布局 formA 引用了 amount → 提示
  - 校验规则 ruleB 依赖 amount → 提示
  - 流程节点 conditionExpr 引用 amount → 提示
  - 权限 dataScope 引用 amount → 提示
```

依赖图存 `lc_meta_dependency`，变更前查询受影响元数据，警告或阻止。

#### 优化3：元数据生命周期治理

元数据有状态：`DRAFT → PUBLISHED → DEPRECATED → ARCHIVED`。
- 废弃的元数据不再加载，但保留可查
- 定期归档清理冗余/无引用的元数据
- 每条元数据记录 `owner`（谁定义的）、`usageCount`（被引用次数），治理可见

#### 优化4：元数据命名空间

按业务域/模块分命名空间（如 `purchase`/`stock`/`finance`），避免全局 metaCode 冲突，支持按命名空间加载/导出（对接应用包）。

#### 优化5：统一元数据 API + 类型 Schema 校验

所有元数据走统一 API（`/api/lowcode/meta/{metaType}` CRUD），但每种 `metaType` 有自己的 JSON Schema 校验（保存前校验合法性，对应"建表校验前置"）。

### 20.4 数据模型

```sql
-- 统一元数据注册表
lc_meta_registry (
  id, metaType,           -- BIZ/FIELD/ACTION/FORM/LIST/REPORT/PERM/WORKFLOW/VALIDATION/NUMBER...
  metaCode, metaName,
  domain,                 -- STRUCTURE/BEHAVIOR/PRESENTATION/CONTROL
  namespace,              -- 业务域命名空间
  layerType, version, status,   -- status: DRAFT/PUBLISHED/DEPRECATED/ARCHIVED
  content,                -- 元数据内容（JSON，按 metaType 有不同 schema）
  owner, usageCount,
  createTime, updateTime
)

-- 元数据依赖图
lc_meta_dependency (
  id, fromMetaId, toMetaId, depType   -- depType: REFERENCE/EXTEND/CONDITION
)

-- 元数据类型 schema（校验用）
lc_meta_type_schema (
  metaType, jsonSchema    -- 每种元数据类型的 JSON Schema
)
```

### 20.5 运行时机制

```
MetaRegistry.load(metaType, metaCode):
  1. 查 lc_meta_registry（按 layerType 合并，见方向1）
  2. 按 domain 路由到子引擎
  3. 子引擎按 content 驱动执行

MetaRegistry.changeImpact(metaId):
  1. 查 lc_meta_dependency 反向依赖
  2. 返回受影响的元数据列表
  3. 标记 BREAKING 的阻止变更，否则警告
```

### 20.6 落地步骤

1. 建 `lc_meta_registry` 统一注册表，把现有 `lc_biz_meta`/`lc_field_meta` 等迁入（metaType=BIZ/FIELD）
2. 按域拆子引擎（现有 CrudExecutor/StateMachine 等已是子引擎，归域即可）
3. 建依赖图，实现变更影响分析
4. 元数据状态机（草稿/发布/废弃）
5. 命名空间划分
6. 统一元数据 API + 各类型 JSON Schema 校验
7. 前端统一元数据管理视图 — **详见前端设计文档**

## 21. 方向三：元数据版本化

### 21.1 苍穹做法

元数据带版本号，变更存历史可回滚，产品升级时客户层自动兼容，有升级工具处理兼容性。

### 21.2 苍穹不足

| 不足 | 问题 |
|------|------|
| **版本粒度粗** | 整业务对象版本，单字段变更也整体新版本，版本爆炸 |
| **兼容靠人工工具** | 字段重命名/类型变更兼容靠升级工具人工处理，易错 |
| **回滚风险** | 回滚元数据可能影响已产生业务数据（字段已存数据，回滚删字段），处理不完善 |
| **多环境同步难** | 开发/测试/生产元数据版本同步靠人工 |

### 21.3 我们的优化

#### 优化1：细粒度版本

版本到**字段/属性粒度**：单字段变更只记该字段的版本变更，不整体新版本。减少版本爆炸，diff 精确。

```
v1.0: 业务对象 purchaseOrder 建立
v1.1: 字段 amount 的 scale 从 2 改到 4   ← 只记这一个属性变更
v1.2: 新增字段 projectCode              ← 只记新增
```

#### 优化2：兼容性自动检测

变更时自动判断破坏性：

| 变更 | 兼容性 | 处理 |
|------|--------|------|
| 新增字段 | COMPATIBLE | 直接通过 |
| 改 label/提示 | COMPATIBLE | 直接通过 |
| 改 type（如 decimal→string） | BREAKING | 要求迁移脚本 |
| 缩 length | BREAKING | 要求迁移脚本 |
| 删字段 | BREAKING | 检查是否有数据，有则要求归档脚本 |

BREAKING 变更必须附迁移脚本，走审批，不静默通过。

#### 优化3：回滚安全检查

回滚前检查业务数据依赖：
- 删字段回滚：该字段已有数据？有则提示"字段有数据，回滚将丢失，需先归档"
- 改 type 回滚：现有数据能否转换？不能则阻止
- 给出回滚影响清单，确认后才执行

#### 优化4：版本 diff 可视化 + 多环境同步走应用包

版本间 diff 可视化（哪个字段哪个属性变了）— **前端详见前端设计文档**。多环境同步走应用包（方向4），不人工同步。

#### 优化5：向前兼容声明

每个版本变更声明 `compatibility`（COMPATIBLE/BREAKING），BREAKING 走审批 + 迁移脚本，COMPATIBLE 自动生效。

### 21.4 数据模型

```sql
-- 元数据版本历史（细粒度）
lc_meta_version (
  id, metaType, metaCode, version,
  changeType,            -- ADD_FIELD/MODIFY_PROP/REMOVE_FIELD/ADD_ACTION...
  changedField,          -- 变更的字段/属性（细粒度）
  oldValue, newValue,    -- 变更前后值
  compatibility,         -- COMPATIBLE / BREAKING
  migrationScript,       -- BREAKING 变更的迁移脚本
  content,               -- 该版本完整内容快照
  createTime, creator, approvedBy
)

-- 回滚安全检查
lc_meta_rollback_check (
  versionId, affectedDataCount, impactSummary, safe
)
```

### 21.5 运行时机制

```
MetaRegistry.change(metaId, change):
  1. 检测兼容性（自动判断 COMPATIBLE/BREAKING）
  2. if BREAKING: 要求 migrationScript + 审批
  3. 变更影响分析（方向2 依赖图）
  4. 写 lc_meta_version（细粒度记录）
  5. 更新 lc_meta_registry.content
  6. 失效合并缓存（方向1）

MetaRegistry.rollback(versionId):
  1. 回滚安全检查（数据依赖）
  2. 不安全则提示影响，确认后执行
  3. 恢复到该版本内容
```

### 21.6 落地步骤

1. `lc_meta_version` 表 + 变更历史记录
2. 兼容性自动检测器
3. BREAKING 变更审批流 + 迁移脚本执行
4. 回滚安全检查
5. 版本 diff 可视化 — **前端详见前端设计文档**
6. 与方向1（分层）协同：PLATFORM 层版本升级，CUSTOMER 自动兼容

## 22. 方向四：应用包

### 22.1 苍穹做法

应用包/开发方案：把一个业务领域的所有产物打包（元数据+插件+页面+权限+流程+配置），整体部署/迁移/升级，有版本。

### 22.2 苍穹不足

| 不足 | 问题 |
|------|------|
| **包内依赖黑盒** | 包引用外部（如标准产品字段），部署时依赖检查不充分 |
| **包升级冲突** | 新版包与已有数据/自定义冲突处理粗 |
| **包不可组合** | 组合多包（采购包+库存包）的依赖处理弱 |
| **缺兼容矩阵** | 包间兼容性不清晰 |

### 22.3 我们的优化

#### 优化1：包依赖声明 + 解析

包显式声明依赖（依赖哪些其他包、标准产品版本），部署时解析依赖树，缺失则报错，版本不匹配则警告。

```json
// manifest.json
{
  "packageCode": "purchase-management",
  "version": "1.2.0",
  "dependencies": [
    { "package": "base-data", "versionRange": ">=1.0.0" },
    { "package": "@platform/standard", "versionRange": ">=2.0.0" }
  ]
}
```

#### 优化2：包组合 + 冲突走分层继承

多包组合时，冲突（都改了同一字段）走**方向1 分层继承**解决，而非简单覆盖。每个包声明自己的 layerType，按层合并。

#### 优化3：增量包

支持增量包：只含相对基线版本的变更，减小体积。部署 = 基线包 + 增量包。

#### 优化4：包版本兼容矩阵

维护包间兼容性矩阵，部署前校验：purchase-management 1.2.0 是否兼容 base-data 1.1.0？不兼容则阻止。

#### 优化5：包与数据分离

包只含结构/配置，**不含业务数据**。数据迁移走单独脚本（方向3 的 migrationScript），避免包携带数据导致的环境数据污染。

#### 优化6：包市场（远期）

业务模板包市场，可发布/引用/安装标准业务包。

### 22.4 数据模型

```sql

lc_app_package (
  id, packageCode, packageName, version,

  layerType,              -- 包对应的层（组合冲突用）
```

## 23. 四方向协同关系

四个方向不是孤立的，互相支撑：

```
方向2（统一元数据）是基础
  ├── 方向1（分层继承）在统一元数据上加 layer 维度
  ├── 方向3（版本化）给统一元数据加版本历史
  └── 方向4（应用包）把统一元数据打包，包内元数据带层+版本

协同场景：
  - 平台发布标准产品 = 应用包（方向4）含 PLATFORM 层（方向1）元数据 + 版本（方向3）
  - 客户定制 = CUSTOMER 层增量元数据 + 插件，打成客户包
  - 运行时 = 统一引擎（方向2）加载各层元数据，按层合并（方向1），按版本（方向3）兼容
  - 升级 = 新版平台包部署，CUSTOMER 层通过继承自动兼容，BREAKING 变更走迁移脚本
```

| 协同点 | 方向 | 说明 |
|--------|------|------|
| 包内元数据带层+版本 | 1+3+4 | 应用包的元数据声明 layerType 和 version |
| 分层合并用统一引擎 | 1+2 | MetaRegistry 统一加载，按层合并 |
| 版本化基于统一元数据 | 2+3 | lc_meta_version 关联 lc_meta_registry |
| 变更影响分析跨域 | 2 | 依赖图跨结构/行为/展现/控制域 |
| BREAKING 变更走包迁移 | 3+4 | 包内 migrations 对接版本化迁移脚本 |

## 24. 元数据优化落地路线图

### 24.1 阶段划分

| 阶段 | 内容 | 依赖 | 里程碑 |
|------|------|------|--------|
| **S1 元数据统一** | 方向2：统一注册表 + 分域子引擎 + 依赖图 | 无 | M1：现有元数据迁入统一注册表，统一 API |
| **S2 分层继承** | 方向1：layer + 属性级覆盖 + 合并 + 缓存 + 溯源 | S1 | M2：客户层加字段不改平台层，合并生效 |
| **S3 版本化** | 方向3：细粒度版本 + 兼容检测 + 回滚安全 | S1 | M3：元数据变更可追溯可回滚，BREAKING 拦截 |
| **S4 应用包** | 方向4：包结构 + 依赖解析 + 部署引擎 | S1+S2+S3 | M4：业务打包部署迁移 |
| **S5 治理增强** | 命名空间 + 生命周期 + 包市场 + diff 可视化 | S1~S4 | M5：元数据治理完整 |

### 24.2 优先级建议

```
S1（统一元数据）是地基，先做
  → S2（分层继承）价值最高，紧接做
  → S3（版本化）配合 S2，可并行
  → S4（应用包）等元数据稳定后做
  → S5（治理）渐进增强
```

**最优先**：S1 + S2。因为"一切皆元数据统一驱动"是地基，"分层继承"是最高价值（解决结构层扩展不改平台）。这两个做完，核心能力就具备了。

### 24.3 与现有方案的整合

| 现有 | 整合到 |
|------|--------|
| `lc_biz_meta`/`lc_field_meta` 等 | 迁入 `lc_meta_registry`（metaType=BIZ/FIELD），加 layerType |
| CrudExecutor/StateMachine/EventBus | 归为结构域/行为域子引擎 |
| 插件机制（第3章） | 保留，插件改行为；分层改结构，互补 |
| 字段变更事件（第13章） | 归行为域元数据，纳入统一管理 |
| 审批流（第16章） | 归控制域元数据 |
| 对外API映射（第15章） | 归行为域元数据 |
| 元数据缓存 | 复用现有基础数据缓存，合并结果缓存其上 |

## 25. 苍穹 vs 本方案优化对照

| 方向 | 苍穹 | 本方案优化点 |
|------|------|-------------|
| 分层继承 | 字段级覆盖、合并黑盒、删除模糊 | **属性级覆盖、声明式合并策略、合并缓存、溯源、显式删除、冲突检测** |
| 统一驱动 | 一个臃肿引擎、耦合难追踪 | **分域子引擎、依赖图影响分析、生命周期治理、命名空间** |
| 版本化 | 粗粒度、兼容靠人工、回滚风险 | **细粒度版本、兼容自动检测、回滚安全检查、向前兼容声明** |
| 应用包 | 依赖黑盒、组合弱 | **依赖声明解析、组合走分层、增量包、兼容矩阵、包数据分离** |

**核心优化理念**：苍穹是"大而全的统一引擎"，本方案是"**分域自治 + 统一注册 + 分层合并 + 版本安全 + 包化部署**"——统一但不臃肿，分层且可溯源，版本化且安全，包化且可组合。

## 28. API 服务管理角色转变（元数据驱动 + 统一网关下）

> 问题背景：未来所有功能通过元数据驱动，所有 CRUD 走统一网关 `POST /api/lowcode/gateway { bizCode, action, payload }`，很多页面的新增/修改/删除接口都一样。当初 API 服务管理（ApiManageView + api/registry.ts + 白名单校验）是为了解决安全漏洞中的越权漏洞。统一网关后还需要 API 服务管理吗？

### 28.1 核心变化：URL 级治理 → bizCode+action 级治理

| 维度 | 现有 | 未来 |
|------|------|------|
| **白名单** | 逐 URL 登记 | 网关 URL 登一条 + 非网关 API 仍逐条 |
| **权限控制** | URL 级（能否访问这个 URL） | **bizCode+action 级**（能否对该业务执行该操作），下沉到网关内部 |
| **ApiManageView** | 管理所有 API 登记 | 管理**非网关 API** + **网关权限矩阵**（bizCode×action→允许角色列表） |
| **api/registry.ts** | 所有 serviceId→url 映射 | 网关一条 + 非网关 API 仍登记 |

统一网关后所有 CRUD 共用一个 URL，URL 级白名单失去意义（要么全放行要么全拦截），越权防护必须下沉到网关内部按 bizCode×action 校验——这正是 G3 权限体系要做的事。

### 28.2 后端改动

#### 28.2.1 新增：权限矩阵表

```sql
-- 网关权限矩阵（bizCode × action → 允许的角色列表）
lc_gateway_permission (
  id, bizCode, action,      -- action: create/update/delete/submit/revoke/query/approve/...
  allowedRoles,             -- 允许的角色列表（JSON 数组，如 ["ROLE_BUYER","ROLE_ADMIN"]）
  deniedRoles,              -- 拒绝的角色列表（黑名单，优先于 allowedRoles）
  layerType, version,       -- 分层 + 版本（对接方向1/3）
  createTime, updateTime
)

-- 字段级权限（G3 权限体系的字段权限部分）
lc_field_permission (
  id, bizCode, fieldName,
  permType,                 -- hidden / readonly / editable
  allowedRoles,
  layerType, version
)

-- 数据行权限（G3 权限体系的数据行权限部分）
lc_data_permission (
  id, bizCode, tableName,
  scopeExpr,                -- 数据过滤表达式（如 "dept = ${user.dept}"）
  allowedRoles,
  layerType, version
)
```

权限矩阵纳入统一元数据管理（方向2，归控制域 CONTROL），存 `lc_meta_registry`（metaType=PERM/GATEWAY_PERM/FIELD_PERM/DATA_PERM, domain=CONTROL）。

#### 28.2.2 网关入口加权限校验

```java
// GenericGatewayController 入口增加权限校验
@PostMapping("/api/lowcode/gateway")
public Result gateway(@RequestBody GatewayRequest req) {
    // 1. 权限校验（新增）：当前用户角色是否有权对 bizCode 执行 action
    if (!permissionService.checkActionPermission(req.getBizCode(), req.getAction(), currentUser)) {
        throw new BizException("无权限执行此操作: " + req.getBizCode() + "." + req.getAction());
    }
    // 2. 数据行权限注入（新增）：把数据过滤表达式注入查询条件
    if ("query".equals(req.getAction())) {
        req.getPayload().put("_dataScope", permissionService.getDataScope(req.getBizCode(), currentUser));
    }
    // 3. 分发到引擎（现有逻辑）
    return gatewayService.dispatch(req);
}
```

```java
// PermissionService（新增）
public class PermissionService {

    // 检查操作权限：当前用户角色是否有权对 bizCode 执行 action
    public boolean checkActionPermission(String bizCode, String action, User user) {
        // 1. 查 lc_gateway_permission（带分层合并，方向1）
        GatewayPermission perm = permissionRegistry.getMerged(bizCode, action);
        // 2. 黑名单优先
        if (perm.getDeniedRoles().stream().anyMatch(user::hasRole)) return false;
        // 3. 白名单校验
        return perm.getAllowedRoles().stream().anyMatch(user::hasRole);
    }

    // 获取数据行权限表达式
    public String getDataScope(String bizCode, User user) {
        DataPermission perm = dataPermissionRegistry.getMerged(bizCode, user.getRoles());
        return perm != null ? perm.getScopeExpr() : null;
    }

    // 检查字段权限（下发前端驱动渲染）
    public FieldPermission getFieldPermission(String bizCode, String fieldName, User user) {
        // 返回 hidden/readonly/editable
    }
}
```

- **API 服务管理不删除，角色转变**：从"所有 API 逐条登记 + URL 级白名单"变为"统一网关一条 + 非网关 API 仍逐条 + 权限下沉到 bizCode×action 级"
- **越权防护不变，粒度下沉**：从 URL 级下沉到业务操作级（bizCode×action），这正是 G3 权限体系
- **非网关 API 保留现有机制**：插件外部调用、文件上传、对外 API 适配层等仍逐条登记 + 白名单校验
- **权限矩阵是元数据**：存 `lc_meta_registry`，分层继承 + 版本化，可配置化管理

## 29. 用友 BIP 借鉴：6 个功能增强

> 通过对比用友 BIP，识别出 6 个平台当前缺失的功能点（业务数据多语言除外，用户暂不需要）。按优先级分 P1/P2。

### 29.1 计算表达式（P1）

**需求**：字段间自动计算，如 `金额 = 单价 × 数量`、`含税金额 = 金额 × (1 + 税率)`。表单中极高频。

**现有**：有 `defaultValueExpr` 和 `conditionExpr`（SpEL），但无字段值变化触发计算的机制。

**后端设计**：

```sql
-- 字段元数据增加计算表达式
lc_field_meta 增加:
  computeExpr,            -- 计算表达式（SpEL，如 "unitPrice * quantity"）
```

```java
public void validateComputeExpr(BizMeta meta, Map<String,Object> data) {
    for (FieldMeta field : meta.getFields()) {
        if (field.getComputeExpr() != null) {
            Object expected = spelEvaluator.evaluate(field.getComputeExpr(), data3);
            Object actual = data.get(field.getFieldName());
            if (!Objects.equals(expected, actual)) {
                throw new BizException("字段" + field.getLabel() + "计算值不匹配");
            }
        }
    }
}
```

### 29.2 批量操作（P1）

**需求**：列表页批量审批/下达/冻结/删除。高频需求。

**现有**：网关只支持单条 action。

**后端设计**：

```java
// 网关增加批量 action
// action: batchCreate / batchUpdate / batchDelete / batchSubmit / batchApprove / batchFreeze
// payload: { ids: ["id1","id2",...], ...其他参数 }

// GenericGatewayController 分发
if (action.startsWith("batch")) {
    List<String> ids = req.getPayload().getIds();
    // 同事务批量执行（编程式事务，复用 TransactionOrchestrator）
    tx.execute(status -> {
        for (String id : ids) {
            engine.execute(bizCode, action.replace("batch",""), id, req.getPayload());
        }
        return null;
    });
}
```

**约束**：批量操作同事务（全成功或全回滚）；单批上限可配置（如 200 条）；批量操作前逐条校验权限（复用第 28 章 PermissionService）。

```java
public void checkFrozen(BizMeta meta, String id, String action) {
```
