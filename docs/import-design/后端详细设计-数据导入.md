## 3. P0：事务断链修复（方案A，随一期实施）

### 3.1 问题

`TransactionOrchestrator.run()` 开启 Spring 事务并绑定连接A，但 `SqlExecutor.getConnection()` 每次从 HikariCP 直取新连接B（autocommit=true），业务 SQL 在连接B上立即提交。commit/rollback 的只是连接A的空事务——**网关所有动作的事务原子性实际未生效**（插件钩子失败不回滚已写数据、validateUniqueChecks 的防重承诺未兑现）。

### 3.2 改动（全部在 bcd-wms-db `SqlExecutor.java`）

**依赖前提（已核实）**：bcd-wms-db 已有 `spring-boot-starter-jdbc`（pom.xml:63），`DataSourceUtils` 零新增依赖。

```java
// (1) 取连接：SqlExecutor.java:67
private Connection getConnection(@Nullable String dbName) throws SQLException {
    HikariDataSource ds = dbConfig.getHikariDataSource(dbName);
    if (ds == null) { throw new SQLException("数据源未找到: dbName=" + dbName + ...); }
    // 原: return ds.getConnection();
    return DataSourceUtils.getConnection(ds);   // 有事务绑定→复用连接；无→行为不变
}

// (2) 新增还连接方法（与 closeQuietly 并列，约 :454 附近）
private void releaseConnection(@Nullable Connection conn, @Nullable String dbName) {
    if (conn == null) return;
    try {
        DataSourceUtils.releaseConnection(conn, dbConfig.getHikariDataSource(dbName));
    } catch (Throwable ignore) { }
}
```

**替换点（已核实全部位置）**：

| 位置（行号） | 所在方法 | 改动 |
|---|---|---|
| :86/:97 | query | `closeQuietly(conn)` → `releaseConnection(conn, dbName)` |
| :121/:139 | query 变体 | 同上 |
| :152/:162 | query 变体 | 同上 |
| :186-:208 | execute（单条） | close 替换；**rollbackQuietly 保留**（对绑定连接 rollback 无害且语义正确） |
| :230-:253 | executeInTransaction | 同上。注意：该方法自带 setAutoCommit(false)，修复后外层已有事务时会复用绑定连接——**需保留**（嵌套 setAutoCommit 幂等），或该方法标注"建议直接被外层事务覆盖" |
| :267/:281 | batch | close 替换 |

`closeQuietly(PreparedStatement/ResultSet)` **不动**（Statement/ResultSet 归属连接，无绑定概念）。

### 3.3 行为矩阵（修复后）

| 场景 | DataSourceUtils 行为 | 效果 |
|---|---|---|
| 无事务（异步导入流水线直接调 batch） | ds.getConnection() 新连接 | 与现状完全一致（自动提交） |
| 网关事务内（TxOrchestrator.run） | 返回线程绑定的连接A | 钩子/查重/INSERT/状态机全在连接A，commit/rollback 真正生效 |
| 非 lowcode 库（dbName≠"lowcode"） | 该 DataSource 无事务绑定 → 新连接 | 行为不变（TxConfig 只管理 lowcode 库） |

### 3.4 连带影响与对策

1. **连接持有时间延长**：原来每条 SQL 独立归还，现在网关动作期间持有到动作结束。实际配置 `maximum-pool-size: 1000`（application.yml:8，远超需求，**无需调整**）；另注意池配置 `auto-commit: false`——原系统依赖 Hikari 归还脏连接时静默 commit（这正是事务空转未被察觉的原因），修复后行为仍等价（releaseConnection→close→Hikari 归还 commit）。
2. **TransactionOrchestrator 加 timeout 重载**：
   ```java
   public Object run(String bizCode, String action, ActionContext ctx, Action body, int timeoutSeconds)
   ```
   原 `run(...)` 委托 `run(..., defaultTimeout)`。同步导入走 120s。
3. **NumberRuleEngine 兼容性**：其 txTemplate/failSafeTxTemplate 已注入 TxConfig 的 transactionManager（见记忆 project-number-rule-backend-generation），与修复方向一致，无冲突；发号 `SELECT FOR UPDATE` 行锁在真事务下语义增强（锁持到业务提交，并发防重号真正兑现）。
4. **PG 25P02 约束升级为全局约束**：事务内任何失败语句 abort 整个事务——网关动作内"try-catch 吞异常继续执行后续 SQL"的存量写法（若有）会炸，修复后需全库排查一次 `catch` 后继续跑 SQL 的模式，改为抛出终止事务或走 REQUIRES_NEW 小事务。
5. **验收标准**：集成测试——网关 create 动作，插件前置钩子抛异常 → 库中无数据；`validateUniqueChecks` 并发双请求 → 仅一条落库；正常 create → 数据落库且网关日志出现 "事务提交成功"。

## 4. P1：元数据同步打通（必填/唯一/codeField）

### 4.1 MetaSyncService（bcd-code `common/MetaSyncService.java`）

`collectFields` 提取逻辑增强（替换写死的 :111-112）：

| 设计器配置 | 提取规则 | 落库列 |
|---|---|---|
| 必填开关 | `props.required === true` 或 `props.validationRules` 含 `type=='required'` | `is_required` |
| 唯一标识 | 控件属性面板"唯一标识"开关 | `is_unique` |
| 联合字段 | "联合字段"多选列表（组合唯一） | `unique_group`（新列，JSON 数组 `["f1","f2"]`） |
| 编码字段 | base-data 控件 `props.codeField`（见前端文档§2） | `base_data_ref` JSON 增加 `codeField` 键 |

**存量兼容**：`base_data_ref` 存量 JSON 无 codeField 键 → 读侧判空即报"字段未配置编码字段"（决策：后端只兜底报错，不猜测回退）。`unique_group` 新列走 MetaRegistry 既有自动补列模式（MetaRegistry.java:36-47 的 ADD COLUMN 逻辑），无需手工刷库。

**清除语义**：同 DEFAULT_VALUE_EXPR 的教训——规则清除时显式写空串/空 JSON，防 upsert 只更新传入字段残留旧值。

### 4.2 MetaRegistry / FieldMeta

- `FieldMeta` 加 `uniqueGroup`（`List<String>` 或 JSON 原文）字段；
- BizMeta 组装时读取，随 reload 生效。

### 4.3 CrudExecutor 消费（激活服务端防重）

`validateUniqueChecks`（:37-92）入口处自动拼装元数据检查项，与前端 `__uniqueChecks` 合并去重：

```
检查项来源：
  ① payload.__uniqueChecks（前端临时传，现状保留）
  ② meta.fields 中 is_unique=true 的字段        → 单字段唯一检查
  ③ unique_group 组合的每组字段                  → 组合唯一检查（任一成员值为 null 的跳过该组，与 PG 唯一索引 NULL 语义对齐）
```

`validateFields`（:561）无需改动——is_required 落库真实值后自动激活。

### 4.4 存量页面

元数据同步是保存触发型：存量页面需**重新保存一次**才同步出 is_required/is_unique/codeField。提供管理接口（二期）：`POST /api/lowcode/meta/resync-all` 遍历 `lowcode_page` 重跑 MetaSyncService；一期在导入报错信息中引导（"该字段未配置编码字段，请到设计器补配并保存页面"）。

## 6. 导入流水线详细设计

### 6.1 模板生成（ImportTemplateService）

**数据源**：`MetaRegistry.getMeta(bizCode)`（字段/主键/keyStrategy）+ 页面 schema 的明细表定义（`lowcode_page` 读 schema → `collectDetailTables` 复用，但只读不建表）+ `base_data_ref`（含 codeField）。

**Sheet 结构**（单表）：
- Sheet1「数据导入」：第1行表头（列头=字段显示名，必填加 `*`）；主键列处理——keyStrategy 为 UUID/SNOWFLAKE 不进模板；业务主键进模板且批注标注"主键列，不可重复"。
- Sheet2「填写说明」：每列一行（列名/所属表/必填/类型/说明/示例）。
- Sheet3「基础资料对照」（有引用列时）：每个被引用基础资料表一个区块，两列——**编码列（codeField 取值，标填充色提示填这列）+ 名称列（displayField 取值）**。

**主从模板（单 Sheet 平铺）**：
- 第1行：合并单元格两个区块标注「主表：xxx（表名）」「明细：xxx（表名）」；
- 第2行：字段表头（主表列 + 明细列并排）；
- 第3行起数据；**主表唯一键列（is_unique 字段或业务主键）为分组锚点**——首行填值开新组，留空归属上一组；
- 明细多表场景（parentType=table 的嵌套明细）：按明细表分区依次平铺（一期支持一级明细 + 二级明细顺序平铺，锚点列规则同）。

**POI 增强**：
- 必填列头红字（`XSSFWorkbook` 样式）；
- 列头批注 `XSSFComment`：类型/格式/示例；基础资料列批注"填编码，如 C-1001"；
- 数据验证下拉 `XSSFDataValidation`：可选值总长 ≤255 字符显式列表；255 < 条数 ≤2000 用对照 Sheet 区间引用公式；超 2000 不做下拉仅对照表；
- 冻结表头 `createFreezePane(0, 2)`（主从）/ `createFreezePane(0, 1)`（单表）；
- 下拉取值：生成模板时实时查一次基础资料表（`SELECT codeField, displayField`，走 helper.query + 列名映射，**批注中标明"校验以库中实时数据为准"**）。

### 6.2 解析与分组（ImportParseService）

- **POI SAX 事件模型**（`XSSFReader` + `ReadOnlySharedStringsTable`，逐行回调），不整本 DOM 驻留——10 万行内存只驻留当前批；
- 表头映射：第2行（主从）/第1行（单表）表头 → 字段名（显示名与字段名都接受，按 `lc_field_meta` 反查）；
- 分组规则：锚点列（唯一键）非空 → 新建 `MasterRecord`；空 → 归属上一组的 `details`；首行明细无主记录 → `RowError(行号, 锚点列, "明细行缺少主记录")`；
- 全空行跳过；单元格值统一 `trim`；
- 类型预转换：按 `lc_field_meta.columnType`（bigint→Long / numeric→BigDecimal / varchar→String / date→多格式尝试 `yyyy-MM-dd`、`yyyy/MM/dd`、`yyyy-MM-dd HH:mm:ss`），失败即 `RowError`；
- **大数处理**：单元格数值超 JS 安全整数的按字符串读（POI `DataFormatter`），主键生成端无此问题（后端 Long）；
- 输出结构：
  ```java
  ParsedDocument {
      List<MasterRecord> records;      // MasterRecord { Map<String,Object> master; Map<String,List<Map>> detailsByTable; int excelRowNo; }
      List<RowError> parseErrors;
      long estimatedTotal;             // dimension 估算
  }
  ```

### 6.3 校验（ImportValidateService）

按批（1000 主记录）执行，错误行剔除后不进入写入：

| 校验 | 数据来源 | 说明 |
|---|---|---|
| 必填 | `is_required` | 空值/纯空白 → 行级错误 |
| 类型/长度 | `columnType` + varchar 长度 | 解析阶段已预转，此处复核长度 |
| Excel 内查重 | `is_unique` / `unique_group` / 业务主键 | 组内 group by 锚点 → "第3、7行 订单编号 SO-001 重复" |
| 库内预查重 | 同上 | `WHERE col IN (整列值)` 批量（500 值/批 IN 分片），复用 P1 打通后的唯一字段元数据 |
| 编码字段配置 | `base_data_ref.codeField` | 空 → **整单报错**（"第X列引用基础资料未配置编码字段，请先在设计器完成配置并保存页面"），任务直接 FAILED |

**NULL 不参与唯一查重**（对齐 PG 唯一索引多 NULL 语义）；匹配精确 + trim，不做 lower() 宽松匹配（宁严勿松）。

**三层防重兜底**：Excel 内查重 → 库内 IN 预查 → DB 唯一索引/主键约束（并发窗口漏过时批事务回滚接住，整批进错误报告）。

### 6.4 基础资料反查（BaseDataReverseResolver + ReverseLookupCache）

```
按列收集显示值（去重 trim）→ 按基础资料表分组
→ 每组一次 IN 查询（500 值/批）：
   SELECT codeField, valueField FROM 基础资料表 WHERE codeField IN (...)
   走 helper.query + queryAndMap 列名映射（大写列名问题）+ quoteIdentifier 路径（带引号大写建表问题）
→ Map<编码, 主键> 存 ReverseLookupCache（任务级，多列同表共享）
→ 逐行替换：编码 → 主键值
```

- **codeField 是唯一匹配依据**（用户决策：前端强制必配，后端空值兜底报错）；
- 类型对齐：反查回的 valueField 值按本表外键列 columnType 转换（BIGINT→Long、VARCHAR→String），沿用 `enrichBaseDataFields` 的 Long/BigInteger 适配逻辑；
- 错误：不存在 → "第5行「客户编码」：'C-9999' 在基础资料中不存在"；多条匹配（codeField 未建唯一索引的重名）→ "匹配到 N 条，请检查基础资料"；基础资料表为空 → 整单报错提示先导基础资料；
- 只处理**本表一级引用**（嵌套点号字段 `WH_KEY.ORG_NAME` 不在导入范围，与现有 enrich 口径一致）；
- **自引用**（上级组织）：按行序拓扑处理——锚点值在前面的组：等该组落库拿主键后回填；引用库中已有：反查；都查不到 → 行级错误。

### 6.5 主从写入（MasterDetailWriter）

**批事务**：1000 主记录一批，`TransactionOrchestrator.run(bizCode, "importCreate", ctx, body, 120)`（P0 新增的 timeout 重载）。

```
每批 body 内：
1. 主表 batchInsert（每批 500 行分片调 SqlEngineFacade.batchInsert）
   - 主键生成遵循 keyStrategy：SNOWFLAKE→SnowflakeIdGenerator.nextId()；UUID→32位串；业务主键→用户填的值（必填校验已保证非空）
   - applyDefaultValues 复用：编码规则字段（DEFAULT_VALUE_EXPR）Excel 留空 → NumberRuleEngine 生成
     （发号走 txTemplate REQUIRED 加入批事务；1000 行/批发号，行锁竞争可控；
       需注意 PG 25P02：批内任何失败语句 abort 批事务 → 整批回滚进错误报告，下一批新事务，行为正确）
2. 每组明细行回填外键列 = 主表主键值（外键列名 = 父表 primaryKeyField，与 BusinessTableSyncService 建表时自动加的关联外键一致）
3. 各明细表按 tableName 分组 batchInsert（明细主键同 keyStrategy 生成）
4. created_at/updated_at 走 autoTimestampColumns（batchInsert 现有能力）
```

**同步模式差异**（<2000 行且无明细）：全部记录**一个事务**，任一行失败整体回滚，返回完整错误清单（用户小文件改完重导成本低）。

**异步模式**：批失败标行号继续下一批，终态 PARTIAL（success>0 且 failed>0）/ FAILED（全败）/ SUCCESS。

**审计**：INSERT 不记 `lc_data_audit_log`（既定策略），导入不接审计。

### 6.6 错误报告文件（ImportErrorCollector）

- 错误累积内存（上限 5000 条，超出聚合为"N 条同类错误"）；
- 终态时用 POI 生成：**原始数据行 + 追加「错误原因」列**（多个错误分号连接），路径存 `error_file_path`；
- 下载接口校验任务归属（created_by）后流式返回；
- 错误原因含主键值时走 String（Snowflake 精度）。

## 7. 异步任务与并发调度

### 7.1 状态机

```
PENDING ──CAS──► RUNNING ──► SUCCESS / PARTIAL / FAILED
   │                │
   │(用户取消)       │(用户取消，批间检查)
   └──► CANCELLED ◄─┘
```

### 7.2 准入三层（ImportTaskService.create 时检查）

| 层 | 规则 | 动作 |
|---|---|---|
| 用户级 | 同 `created_by` 存在非终态任务 | 拒绝："您有导入任务进行中/排队中" |
| 表级 | 同 `biz_code` 存在非终态任务（**PENDING 也占用**） | 拒绝："该表已有导入任务排队" |
| 全局 | RUNNING 数 < maxConcurrent(默认2) | 超出 → PENDING 排队（不拒绝） |

### 7.3 调度器（ImportTaskScheduler，参照 WorkflowScheduler）

```
@Scheduled(fixedDelay = 2000)
1. SELECT COUNT(*) WHERE status='RUNNING'
2. < maxConcurrent → 按 created_at ASC 捞 PENDING（捞差额数）
3. UPDATE ... SET status='RUNNING', started_at=now() WHERE task_id=? AND status='PENDING'
   → 影响行数=1 才提交线程池（CAS 原子，天然兼容未来多实例）
```

线程池：`ThreadPoolTaskExecutor`，core=max=maxConcurrent，`SynchronousQueue`，线程名 `import-executor-N`，独立于 HTTP/工作流线程。

### 7.4 进度与取消

- 进度节流：每批（1000 行）更新一次 `processed_rows/success_rows/failed_rows`——10 万行仅 100 次写库；
- 取消：置 `cancel_flag`（任务表加列 `cancel_flag SMALLINT DEFAULT 0`），流水线批间检查 → CANCELLED；RUNNING 中已提交的批不回滚（保留）；
- 排队位置：`COUNT(*) WHERE status='PENDING' AND created_at < 我的created_at`。

### 7.5 崩溃恢复与清理

- 启动监听：RUNNING → FAILED（"服务重启中断，请重新导入"）；**PENDING 保留**（调度器自动继续捞）；
- 暂存文件：`data/import/{taskId}.xlsx`；终态 7 天后由调度器顺带清理（文件 + error_file）；
- ImportFileStore 接口抽象存取（一期 `LocalFileStore` 实现），多实例演进时换共享存储实现，流水线零改动。

### 7.6 分流阈值

上传时 POI 读 sheet dimension（`<dimension ref="A1:H100001"/>`）毫秒级估行数：<2000 主记录且无明细 → 同步执行（事务内完成直接返回结果）；否则建 PENDING 任务返回 taskId。**分流不精确没关系**（dimension 误差 ±few rows），同步路径也全程走同一流水线（只是同步等待完成）。

## 8. 接口定义（ImportController，前缀 /api/lowcode/import）

鉴权沿 bcd-code 现有 Controller 拦截机制（与 PageController/PluginController 一致），`created_by` 取现有用户上下文。

### 8.1 下载模板
```
GET /template?bizCode={bizCode}
响应: xlsx 二进制流
  Content-Disposition: attachment; filename*=UTF-8''导入模板-{业务名}.xlsx
```

### 8.2 执行导入
```
POST /execute   multipart/form-data
  file: .xlsx（≤20MB）
  bizCode: string
  响应(同步): { "sync": true, "result": { "totalRows":1500, "successRows":1500, "failedRows":0, "errors":[] } }
  响应(异步): { "sync": false, "taskId": "9f2c...", "queuePosition": 1 }
```

### 8.3 任务进度
```
GET /task/{taskId}
响应: { taskId, bizCode, status, totalRows, processedRows, successRows, failedRows,
        queuePosition, errorMsg, startedAt, finishedAt, hasErrorFile: true }
```

```
GET  /task/{taskId}/errors        → xlsx 流（归属校验）
POST /task/{taskId}/cancel        → { ok: true }
GET  /tasks?bizCode=&pageNum=&pageSize=   → 分页列表（按 created_by 过滤，倒序）
```

**错误透传原则**：所有失败（准入拒绝、解析异常、流水线失败）返回明确 `errorMsg` 给前端展示，不吞异常——沿用 `BizException` + 全局异常处理模式。

## 10. 多数据库兼容注意点（7 库）

| 点 | 处理 |
|---|---|
| lc_import_task 建表 | dialect 懒建表（checkTableExistsSql），TIMESTAMP/索引由 dialect 生成 |
| 反查/查重 SQL | 全部走 `SqlEngineJson/helper`（自带 quoteIdentifier 方言处理），**禁止裸拼表名**（带引号大写建表 + PG 折叠小写 + Oracle 折叠大写） |
| helper.query 大写列名 | 反查结果取值用 queryAndMap/列名映射，不能按原列名直取 |
| 导入后统计信息 | 仅 PG 执行 `ANALYZE 表名`（dialect 判断）；Oracle 的 DBMS_STATS / 其他库跳过（统计过期只影响性能不影响正确性，二期补方言适配） |
| IN 分片 | 500 值/批（Oracle 1000 上限内、SQLite 变量数限制内取保守值） |

## 13. 风险与开放问题

1. **P0 修复的回归面**：SqlExecutor 是全部数据访问的底座，修复后需全库回归（网关 CRUD、工作流、编码规则、页面保存建表）；重点盯 §3.4 第 4 点（吞异常继续跑 SQL 的存量模式）。
2. 插件钩子一期不拦截导入：若某表配了强校验钩子（如库存扣减），导入会绕过——文档明确该边界，二期提供"导入走网关动作"可选项。
3. 主从模板多级明细（parentType=table 嵌套）一期只做顺序平铺，交互复杂度高的场景引导拆文件。
4. `codeField` 需用户给 base-data 控件加编码字段属性（前端先行，见前端文档§2）；存量页面全部要补配 + 重新保存——建议上线公告引导。
