# 元数据架构优化 — 前端改动方案

> 版本：v1.0
> 日期：2026-09-24
> 关联：元数据驱动架构优化设计文档（四个方向）
> 目标：明确四个方向与**现有前端低代码平台**的关系，及前端具体改什么、怎么改
> 原则：**在现有代码基础上扩展，不另起炉灶**

---

## 0. 与现有前端的关系（不是独立的一套）

四个方向**全部基于现有前端扩展**，不是另起炉灶：

| 方向 | 现有前端基础 | 改动性质 |
|------|------------|----------|
| 1. 分层继承 | 现有 PageSchema/ComponentSchema 单层 | **扩展现有 schema 类型** + 设计器加层切换 |
| 2. 统一元数据 | 现有 PropertyPanel 的 events/validation 标签页已配部分元数据；PageManageView 已是管理界面 | **扩展现有标签页** + 新增统一元数据管理视图（复用 PageManageView 模式） |
| 3. 版本化 | 现有 PageSchema 已有 version 字段 | **扩展 version** + 新增版本历史/diff/回滚组件 |
| 4. 应用包 | 现有 savePage 单页面保存 | **新增包管理视图**（复用 PageManageView 模式）+ 打包入口 |

**核心**：现有设计器（DesignerView）、属性面板（PropertyPanel）、页面管理（PageManageView）、designerStore、schema 类型**全部保留并扩展**，不重写。

## 2. 方向一：元数据分层继承 — 前端改动

### 2.1 改什么

| 文件 | 改动 | 基于现有什么扩展 |
|------|------|-----------------|
| `src/types/schema.ts` | PageSchema 加 `layerType`/`parentPageId`；ComponentSchema 加 `layerType`/`overrideProps`/`isNew`/`isRemoved` | 扩展现有 PageSchema/ComponentSchema 接口 |
| `src/store/designer.ts` | 加 `currentLayer` 状态；加 `setLayer()`/`overrideProp()`/`markFieldNew()`/`markFieldRemoved()`/`getMergedSchema()`；`exportSchema()` 按层导出增量 | 扩展现有 designerStore + exportSchema |
| `src/components/designer/PropertyPanel.vue` | 客户层编辑属性时标记"覆盖"，显示产品层原值对比；加"恢复原值"按钮 | 扩展现有属性编辑逻辑 |
| `src/views/DesignerView.vue` | 顶部加层选择器（PLATFORM/INDUSTRY/CUSTOMER）+ "合并预览/当前层"切换 | 扩展现有顶部工具栏 |
| **新建** `src/components/designer/LayerDiffDialog.vue` | 层间 diff 可视化（产品层 vs 客户层覆盖了什么） | 复用现有弹窗模式（如 ColumnEditorDialog） |

### 2.2 怎么改（关键代码示意）

**schema.ts 扩展**：
```ts
export type MetaLayer = 'PLATFORM' | 'INDUSTRY' | 'CUSTOMER'

export interface ComponentSchema {
  // ...现有字段保留
  layerType?: MetaLayer              // 新增：该节点所属层
  overrideProps?: Record<string, unknown>  // 新增：本层覆盖的属性（属性级，只记改的）
  isNew?: boolean                    // 新增：本层新增的字段
  isRemoved?: boolean                // 新增：本层显式删除下层字段
}

export interface PageSchema {
  // ...现有字段保留
  layerType?: MetaLayer              // 新增
  parentPageId?: string              // 新增：继承的父层页面
}
```

**designerStore 扩展**：
```ts
// src/store/designer.ts
designerStore.currentLayer = 'CUSTOMER' as MetaLayer   // 新增状态

// 新增方法
export function setLayer(layer: MetaLayer) { ... }      // 切换编辑层
export function overrideProp(id, prop, value) {          // 客户层覆盖属性（记到 overrideProps）
  const node = findNode(...)
  if (!node.overrideProps) node.overrideProps = {}
  node.overrideProps[prop] = value                       // 只记改的属性，不整字段覆盖
}
export function restoreProp(id, prop) {                  // 恢复到产品层原值
  delete node.overrideProps[prop]
}
export function getMergedSchema(): ComponentSchema[] {   // 合并预览（调后端合并或前端合并）
  return apiCall('/api/lowcode/meta/merged', { pageId, layers: [...] })
}
// exportSchema() 改造：客户层只导出增量（isNew/overrideProps/isRemoved），不导全量
```

**PropertyPanel 覆盖标记**：
```vue
<!-- 客户层编辑时，显示覆盖标记 + 原值对比 -->
<div v-if="isOverride(prop)" class="override-badge">覆盖</div>
<span class="orig-value">原值: {{ getOrigValue(prop) }}</span>
<button @click="restoreProp(selectedId, prop)">恢复原值</button>
```

### 2.3 用户体验

- 设计器顶部多一个层选择器：选 PLATFORM 编辑标准产品，选 CUSTOMER 编辑客户定制
- 客户层编辑时，只看到增量（新增的字段、覆盖的属性高亮），可切换"合并预览"看最终效果
- 改一个属性时显示"覆盖了产品层的原值 XXX"，可一键恢复

## 3. 方向二：一切皆元数据统一驱动 — 前端改动

### 3.1 改什么

| 文件 | 改动 | 基于现有什么扩展 |
|------|------|-----------------|
| **新建** `src/views/MetaManageView.vue` | 统一元数据管理（按域分类：结构/行为/展现/控制） | **复用 PageManageView 的列表+编辑模式** |
| **新建** `src/types/meta.ts` | 元数据类型定义（MetaItem：metaType/domain/layerType/version/status/content） | 新类型文件 |
| **新建** `src/store/meta.ts` | 元数据 store（CRUD），仿 designerStore | 复用 designerStore 模式 |
| `src/components/designer/PropertyPanel.vue` | events 标签页扩展（事件订阅配置，不只是写 JS）；validation 标签页扩展（结构化校验规则）；新增 permissions 配置 | **扩展现有 events/validation 标签页** |
| **新建** `src/components/designer/FieldEventRuleDialog.vue` | 字段变更事件配置（第 13 章） | 复用 ColumnEditorDialog 弹窗模式 |
| `src/api/index.ts`（或 persistence.ts） | 加元数据统一 API（/api/lowcode/meta/{metaType}） | 扩展现有 apiCall |

### 3.2 怎么改

**关键认知**：现有 PropertyPanel 的 events/validation 标签页**已经在配置部分元数据**（事件绑定、校验），只是散在页面 schema 里。方向2 是把这些**提升为统一元数据**，并扩展更多类型（权限/流程/报表/编号）。

**PropertyPanel events 标签页扩展**（现有是写 JS 代码，扩展为结构化事件订阅）：
```vue
<!-- 现有：只写 JS 代码 -->
<textarea v-model="eventCode" />

<!-- 扩展后：加"字段变更事件"结构化配置入口 -->
<button @click="openFieldEventRuleDialog()">配置字段变更事件</button>
<FieldEventRuleDialog v-model="fieldEventRules" />
```

**MetaManageView（新建，复用 PageManageView 模式）**：
```vue
<!-- src/views/MetaManageView.vue -->
<template>
  <div class="meta-manage">
    <!-- 按域分类的树/标签 -->
    <MetaDomainTree :domains="['structure','behavior','presentation','control']" />
    <!-- 元数据列表（复用 PageManageView 的 dx-data-grid） -->
    <DxDataGrid :data-source="metaList" />
    <!-- 元数据编辑（按 metaType 动态渲染表单） -->
    <MetaEditDialog :meta-type="selectedType" :content="selectedContent" />
  </div>
</template>
```

**路由**：在现有 router 加 `/meta-manage` → MetaManageView（与 /page-manage 并列）。

### 3.3 与现有管理视图的关系

现有 ApiManageView/CacheManageView/LangManageView/SystemManageView/ThemeManageView 是**特定管理界面**，保留。MetaManageView 是**统一元数据入口**，可：
- 阶段1：并存（MetaManageView 管理新增的元数据类型，现有视图管各自的）
- 阶段2：逐步整合（把现有视图的管理迁入 MetaManageView 统一框架）

**不推翻现有视图**，是新增 + 渐进整合。

### 4.2 怎么改

**BREAKING 变更检测**（在 PropertyPanel 改属性时）：
```ts
// 改字段 type 时
function onFieldTypeChange(newType) {
  if (isBreakingChange(oldType, newType)) {
    // 用 Element Plus 弹窗（不用 alert，符合现有规范）
    openBreakingChangeDialog({
      change: '字段类型变更',
      impact: '已有数据可能无法转换，需迁移脚本',
      requireMigration: true
    })
  }
}
```

**VersionHistoryPanel**：
```vue
<template>
  <div class="version-history">
    <DxDataGrid :data-source="versions" :columns="['version','changeType','compatibility','time','operator']" />
    <button @click="showDiff(v1, v2)">对比</button>
    <button @click="rollback(v(versions[0])">回滚到此版本</button>
  </div>
</template>
```

## 7. 落地顺序（前端）

## 8. 关键约束（遵循现有规范）

- 弹窗用 Element Plus，**不用浏览器原生 alert/confirm**（现有规范）
- 后端失败必须透传前端展示（现有规范），元数据保存失败要提示
- 字段名等约束前端&前端输入时校验（现有规范）
- 改代码后跑 `npm run build` 验证（现有 AGENTS.md 要求）
- 命名 camelCase（现有规范）
