# 业务流后端设计文档

## 1. 背景与目标

### 1.1 工作流 vs 业务流

| | 工作流（审批流）✅ 已有 | 业务流 ❌ 需增强 |
|---|---|---|
| 编排对象 | **人**（审批节点间流转） | **事**（单据间流转） |
| 范围 | 单个单据内部 | 跨多个单据 |
| 例子 | 采购单→经理审批→总监审批→通过 | 销售订单→审核→销售出库单→财务应收单 |
| 表 | `lc_workflow_def/instance/task` | 复用相同表，`workflow_type='bizFlow'` 区分 |

### 1.2 现状分析

现有代码已具备良好基础：

| 能力 | 现状 | 文件 |
|---|---|---|
| 表结构 | ✅ 4张表已建，`workflow_type`/`params`/`control` 字段已有 | `lowcode_tables.sql:383-442` |
| 流程定义 CRUD | ✅ 保存/删除/列表 | `WorkflowService.java:22-88` |
| 流程校验 | ✅ 基础校验（开始/结束节点、连线完整性） | `WorkflowService.java:91-138` |
| 流程发布 | ✅ 校验+启用+保存 | `WorkflowService.java:141-149` |
| 流程启动 | ✅ 创建实例+从开始节点执行 | `WorkflowService.java:152-201` |
| 审批操作 | ⚠️ approve/reject 更新状态，transfer/countersign 只插记录 | `WorkflowService.java:258-290` |
| 待办列表 | ⚠️ 未处理 type 参数（待办/已办） | `WorkflowService.java:293-301` |
| **节点执行引擎** | ❌ **只处理 end/userTask，其他节点类型直接往下走** | `WorkflowService.java:204-255` |
| **业务流启动触发** | ❌ **无按单据操作/按事件启动的触发机制** | 需新增 |
| **跨单据编排** | ❌ **billTask 节点未实现自动创建/操作下游单据** | 需新增 |
| **流程变量** | ❌ **节点间无数据传递机制** | 需新增 |

### 1.3 目标

在现有工作流框架上增强为业务流，不新建表，不引入第三方流程引擎。保留8种节点类型：开始/结束/单据/人工/自动/消息/等待/网关。暂缓子流程，不需要RPA。

## 2. 数据模型

### 2.1 复用现有表

业务流与审批流共用 `lc_workflow_def` 表，通过 `workflow_type` 字段区分：

- `workflow_type = 'approvalFlow'`：审批流（现有行为不变）
- `workflow_type = 'bizFlow'`：业务流（本次增强）

### 2.2 新增字段

`lc_workflow_instance` 表新增 `variables` 字段存储流程变量：

```sql
ALTER TABLE lc_workflow_instance ADD COLUMN variables TEXT;
```

`variables` 存储 JSON 对象，如 `{"orderId":"123","amount":5000,"status":"approved"}`，在节点间传递。

### 2.3 节点配置（nodes 字段内）

每种节点类型的配置已在前端类型定义中完成（`types/workflow.ts`），后端只需解析执行：

| 节点类型 | 关键配置 | 执行逻辑 |
|---|---|---|
| `start`/`end` | 无 | 开始/结束流程实例 |
| `billTask` | `billCode`（单据编码）+ `billAction`（操作如 create/audit/submit） | 调用统一网关执行单据操作 |
| `userTask` | `approverRoles`/`approverUsers`/`approvalMode` | 创建待办任务，等待人工审批 |
| `autoTask` | `executeExpr`（插件标识或表达式） | 调用插件或执行表达式 |
| `messageTask` | `messageType`/`messageReceivers`/`messageTemplate` | 发送消息通知 |
| `waitTask` | `waitDuration`（毫秒）/ `waitCondition` | 等待条件满足或超时后继续 |
| `gateway` | `gatewayType`（exclusive/parallel/inclusive）+ `branches`（分支条件） | 条件路由 |

## 3. 核心设计：节点执行引擎增强

### 3.1 现有代码

### 3.2 增强后的 executeNode

```java
private void executeNode(String instanceId, JSONObject node, JSONArray nodes, JSONArray transitions,
                         String bizCode, String bizId, String initiator,
                         JSONObject variables) throws Exception {
    String type = node.getString("type");
    String nodeId = node.getString("id");

    // 记入实例当前节点
    updateInstanceCurrentNode(instanceId, nodeId);

    switch (type) {
        case "end":
            completeInstance(instanceId);
            return;
        case "userTask":
            createUserTask(instanceId, node, bizCode, bizId, initiator);
            return;  // 等待人工审批，不自动往下走
        case "billTask":
            executeBillTask(node, variables);
            break;  // 执行完自动往下走
        case "autoTask":
            executeAutoTask(node, variables);
            break;
        case "messageTask":
            executeMessageTask(node, variables);
            break;
        case "waitTask":
            executeWaitTask(instanceId, node, variables);
            return;  // 等待条件满足，不自动往下走
        case "gateway":
            // 网关：按条件选择分支往下走
            executeGateway(instanceId, node, nodes, transitions, bizCode, bizId, initiator, variables);
            return;
        default:
            break;
    }

    // 非终止节点：继续执行后续节点
    proceedToNext(instanceId, node, nodes, transitions, bizCode, bizId, initiator, variables);
}
```

### 3.3 各节点类型执行逻辑

#### 3.3.1 billTask（单据节点）

```java
private void executeBillTask(JSONObject node, JSONObject variables) throws Exception {
    String billCode = node.getString("billCode");
    String billAction = node.getString("billAction");  // create/audit/submit/delete
    // 调用统一网关执行单据操作
    JSONObject payload = new JSONObject();
    payload.put("bizCode", billCode);
    payload.put("action", billAction);
    payload.put("payload", variables);  // 流程变量作为单据数据来源
    httpRequest("/api/lowcode/gateway", payload);
    // 将操作结果写入流程变量
    variables.put(billCode + "_result", result);
}
```

**跨单据编排核心**：billTask 节点通过 `billCode` 指定要操作的单据，通过 `billAction` 指定操作类型（create/audit/submit），通过流程变量 `variables` 传递数据。例如：销售订单审核后，billTask 节点自动创建销售出库单。

#### 3.3.2 autoTask（自动节点）

```java
private void executeAutoTask(JSONObject node, JSONObject variables) throws Exception {
    String executeExpr = node.getString("executeExpr");
    // executeExpr 可以是插件标识（如 "plugin:calcTax"）或表达式
    if (executeExpr.startsWith("plugin:")) {
        String pluginId = executeExpr.substring(7);
        // 调用插件管理器执行插件
        pluginManager.execute(pluginId, variables);
    } else {
        // 执行表达式（复用现有 SpEL 或 JS 引擎）
        Object result = expressionEngine.eval(executeExpr, variables);
        variables.put("_autoResult", result);
    }
}
```

#### 3.3.3 messageTask（消息节点）

```java
private void executeMessageTask(JSONObject node, JSONObject variables) throws Exception {
    String messageType = node.getString("messageType");  // email/sms/im/webhook
    JSONArray receivers = node.getJSONArray("messageReceivers");
    String template = node.getString("messageTemplate");
    // 复用现有消息通知机制（RocketMQ + 通知模板）
    notificationService.send(messageType, receivers, template, variables);
}
```

#### 3.3.4 waitTask（等待节点）

```java
private void executeWaitTask(String instanceId, JSONObject node, JSONObject variables) throws Exception {
    long duration = node.getLongValue("waitDuration");
    String condition = node.getString("waitCondition");
    if (duration > 0) {
        // 定时等待：延迟 duration 毫秒后继续
        // 实现：在 lc_workflow_instance 中记录 resume_at 时间，
        // 由定时任务扫描到期实例并恢复执行
        updateInstanceResumeAt(instanceId, System.currentTimeMillis() + duration);
    } else if (condition != null && !condition.isEmpty()) {
        // 条件等待：记录等待条件，由事件触发时检查
        updateInstanceWaitCondition(instanceId, condition);
    }
    // 不自动往下走，等待外部触发恢复
}
```

#### 3.3.5 gateway（网关节点）

```java
private void executeGateway(String instanceId, JSONObject node, JSONArray nodes, JSONArray transitions,
                            String bizCode, String bizId, String initiator,
                            JSONObject variables) throws Exception {
    String gatewayType = node.getString("gatewayType");
    JSONArray branches = node.getJSONArray("branches");

    if ("exclusive".equals(gatewayType)) {
        // 排他网关：只走第一个满足条件的分支
        for (int i = 0; i < branches.size(); i++) {
            JSONObject branch = branches.getJSONObject(i);
            if (evalCondition(branch.getString("condition"), variables)) {
                proceedToSpecificNext(instanceId, node, branch.getString("id"),
                    nodes, transitions, bizCode, bizId, initiator, variables);
                return;
            }
        }
    } else if ("parallel".equals(gatewayType)) {
        // 并行网关：同时走所有出口
        for (int i = 0; i < transitions.size(); i++) {
            JSONObject tr = transitions.getJSONObject(i);
            if (node.getString("id").equals(tr.getString("from"))) {
                proceedToSpecificNext(instanceId, node, tr.getString("to"),
                    nodes, transitions, bizCode, bizId, initiator, variables);
            }
        }
    }
    // inclusive 网关：走所有满足条件的分支（略）
}
```

### 3.4 流程变量传递

`variables` 存储在 `lc_workflow_instance.variables` 字段中，JSON 格式。每个节点执行时：
1. 读取当前 variables
2. 执行节点逻辑，可能写入新的变量
3. 更新 instance.variables

节点间数据流示例：
```
开始 → variables: {orderId: "SO001"}
单据(销售订单.审核) → variables: {orderId: "SO001", orderStatus: "audited"}
单据(销售出库单.创建) → variables: {orderId: "SO001", orderStatus: "audited", outId: "OUT001"}
单据(财务应收单.创建) → variables: {..., arId: "AR001"}
结束
```

## 4. 业务流启动触发

### 4.1 按单据操作启动

当单据执行某操作（如审核/提交）时，检查是否有业务流绑定该单据+操作作为启动条件。

**触发入口**：在统一网关 `POST /api/lowcode/gateway` 中，单据操作完成后追加触发检查：

```java
// GatewayController 或 GatewayService 中，单据操作完成后
private void checkBizFlowTrigger(String bizCode, String action, String bizId, String operator) {
    // 查询所有 enabled 的业务流定义
    JSONArray bizFlows = helper.query("lc_workflow_def",
        new String[]{"id", "code", "name", "control"},
        helper.eq("workflow_type", "bizFlow").addAll(helper.eq("enabled", true)),
        null, false);

    for (int i = 0; i < bizFlows.size(); i++) {
        JSONObject wf = bizFlows.getJSONObject(i);
        String controlStr = wf.getString("control");
        if (controlStr == null) continue;
        JSONObject control = JSON.parseObject(controlStr);
        JSONArray startConds = control.getJSONArray("startByBillAction");
        if (startConds == null) continue;

        for (int j = 0; j < startConds.size(); j++) {
            JSONObject cond = startConds.getJSONObject(j);
            if (bizCode.equals(cond.getString("billCode")) && cond.getBooleanValue("allowed")) {
                // 启动业务流实例
                startWorkflow(wf.getString("code"), bizCode, bizId, operator);
                return;  // 只启动第一个匹配的业务流
            }
        }
    }
}
```

### 4.2 按事件启动

当字段变更事件触发时，检查是否有业务流绑定该事件作为启动条件。复用现有 `lc_field_change_event` 机制。

## 5. 审批操作增强

### 5.1 现有问题

- `transfer`/`countersign` 只插审批记录，未更新任务 assignee 或创建新任务
- 审批通过后未自动继续执行后续节点

### 5.2 增强方案

```java
public void approvalAction(JSONObject data) throws Exception {
    // ... 现有记录插入逻辑 ...

    if ("approve".equals(action)) {
        // 更新任务状态
        updateTaskStatus(instanceId, "DONE");
        // 继续执行后续节点（关键：审批通过后自动往下走）
        resumeWorkflow(instanceId);
    } else if ("reject".equals(action)) {
        updateTaskStatus(instanceId, "REJECTED");
        updateInstanceStatus(instanceId, "REJECTED");
    } else if ("transfer".equals(action)) {
        // 转办：更新任务 assignee
        String targetUser = data.getString("targetUser");
        updateTaskAssignee(instanceId, targetUser);
    } else if ("countersign".equals(action)) {
        // 加签：创建新任务给加签人
        String targetUser = data.getString("targetUser");
        createAdditionalTask(instanceId, targetUser);
    }
}

private void resumeWorkflow(String instanceId) throws Exception {
    // 查询实例当前节点
    JSONObject instance = getInstance(instanceId);
    String currentNodeId = instance.getString("current_node");
    // 查询流程定义
    JSONObject wf = getWorkflowDef(instance.getString("workflow_code"));
    JSONArray nodes = JSON.parseArray(wf.getString("nodes"));
    JSONArray transitions = JSON.parseArray(wf.getString("transitions"));
    JSONObject variables = JSON.parseObject(instance.getString("variables"));
    // 找到当前节点，继续执行后续
    JSONObject currentNode = findNodeById(nodes, currentNodeId);
    proceedToNext(instanceId, currentNode, nodes, transitions,
        instance.getString("biz_code"), instance.getString("biz_id"),
        instance.getString("initiator"), variables);
}
```

## 6. 待办列表增强

### 6.1 现有问题

前端传 `{ type: 'todo'/'done' }` 区分待办/已办，但后端 `listTodo` 只按 `status=PENDING` 查询。

### 6.2 增强方案

```java
public JSONArray listTodo(String assignee, String type) throws Exception {
    String[] cols = { "id", "biz_code", "biz_id", "title", "workflow_name", "current_node", "initiator", "created_at" };
    JSONArray conditions = new JSONArray();
    if (assignee != null && !assignee.isEmpty()) {
        conditions.addAll(helper.eq("assignee", assignee).subList(1, 2));
    }
    if ("done".equals(type)) {
        conditions.addAll(helper.eq("status", "DONE").subList(1, 2));
    } else {
        conditions.addAll(helper.eq("status", "PENDING").subList(1, 2));
    }
    return helper.query("lc_workflow_task", cols, conditions, "created_at", true);
}
```

## 7. 等待节点定时恢复

### 7.1 定时扫描

新增定时任务，扫描 `lc_workflow_instance` 中 `status='WAITING'` 且 `resume_at` 到期的实例，恢复执行：

```java
@Scheduled(fixedDelay = 10000)  // 每10秒扫描一次
public void resumeWaitingInstances() {
    JSONArray instances = helper.query("lc_workflow_instance",
        new String[]{"id", "workflow_code", "current_node", "biz_code", "biz_id", "initiator", "variables"},
        helper.eq("status", "WAITING").addAll(helper.lt("resume_at", Instant.now().toString())),
        null, false);

    for (int i = 0; i < instances.size(); i++) {
        JSONObject inst = instances.getJSONObject(i);
        try {
            resumeWorkflow(inst.getString("id"));
        } catch (Exception e) {
            log.error("[BizFlow] 恢复等待实例失败: {}", inst.getString("id"), e);
        }
    }
}
```

## 10. 风险分析

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| billTask 调用统一网关可能循环触发 | 死循环 | 检查 billCode+action 是否与当前流程实例的触发条件相同，相同则跳过 |
| 并行网关同时执行多个分支 | 数据竞争 | 每个分支共享同一 variables 副本，分支完成后合并 |
| 等待节点定时扫描性能 | 数据库压力 | 扫描间隔10秒，只查 `status='WAITING'` 且 `resume_at` 到期的记录，加索引 |
| 流程变量 JSON 过大 | 存储溢出 | variables 字段用 TEXT 类型，限制单个变量值大小 |
| 审批通过后自动继续执行可能失败 | 流程卡住 | 记录执行日志，失败时实例状态设为 ERROR，支持手动重试 |

## 11. 与现有系统的关系

- **统一网关**：billTask 通过统一网关 `POST /api/lowcode/gateway` 执行单据操作，复用现有 bizCode×action 越权防护
- **插件机制**：autoTask 通过 `plugin:xxx` 标识调用插件，复用现有插件管理器
- **消息通知**：messageTask 复用现有 RocketMQ + 通知模板机制
- **字段变更事件**：按事件启动复用现有 `lc_field_change_event` 机制
- **审批流**：业务流中 userTask 节点的审批操作复用现有 ApprovalBar/ApprovalDialog/TransferDialog
- **不引入第三方流程引擎**：与 P0 决策"自研审批"一致
